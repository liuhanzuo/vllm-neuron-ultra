# Nano4B：保留 six.moves 的正常模块别名行为

本轮为真实 SDK 接入准备了 six.moves 的明确别名规则，修复了我们严格模块核验逻辑中的一个兼容缺口。三组共 52 项检查通过：18 项别名与静态规则检查、16 项模块核验回归、18 项实际子进程启动回归。

尚未执行安装的 six 或真实 SDK。测试使用生成的模拟包和 Python 原有导入流程，不能据此宣称 SDK 或模型已验证完成，也没有新增提速数字。

## 发现的行为

安装的 six 1.17 源码会把自身设置成具有空搜索路径的虚拟包。six.moves 中的一部分名称是已有模块的别名：例如多个别名可以指向同一个真实模块，加载器直接返回原对象。

CPython 3.10 随后会将这个对象的 __spec__ 改为本次别名的导入描述，即使它已经通过原名字加载。因此，“同一已加载模块的导入描述必须永远不变”的规则会误拒绝正常导入。这是我们新增核验逻辑需要处理的兼容行为，不能据此认定 six 或上游模型有缺陷。

新规则先核验原目标模块，再记录本次实际选择的别名 spec 对象。只有这个确切对象、原字段和对应的检查加载器，才能解释目标模块的 spec 变化；原模块对象、文件和其他导入信息仍需匹配。另一个内容看似相同的 spec，或对原 spec 字段、加载器的修改，都不会被自动接受。

## 原始别名表与检查

从安装源码静态提取了 Python 3.10/Linux 使用的 54 个名称：42 个指向真实模块的别名，12 个属于七个原始合成模块组的名称。源码里的覆盖顺序保留，例如 urllib 的部分最初声明会被后面的合成模块注册覆盖。Windows 专属的 winreg 没有加入本机规则。

提取器只解释明确的字面量和版本、平台条件，没有执行 six。生成的完整 54 项注册表经过对象绑定检查，也没有为了测试去加载全部目标模块。

| 正常行为 | 对应检查 |
| --- | --- |
| six 自身变为具有空路径的虚拟包 | 仅允许原源码声明的空路径变化 |
| 已加载目标被 six.moves 复用 | 对象身份保留，spec 变化必须对应实际授权的别名导入 |
| 两个合成模块名称指向同一对象 | 保留共享对象，接受已记录的别名 spec |
| 删除别名后重新导入 | 保留旧、新两次确切 spec 的证据，目标对象继续复用 |
| 可选目标模块不存在 | 保留原 ImportError 与上层回退 |

测试同时拒绝注册表条目替换、目标名称变化、额外路径、未经登记的别名、模块文件变化、伪造或修改的 spec。预加载模块核验新增的例外默认关闭，必须由这个明确的别名规则授权；其他模块替换和来源修改仍然失败。

## 接入边界

实际代码、解释器、预加载模块与原生目标的来源认证仍由具体运行策略完成。这里的源码加载器和元数据身份检查本身不能证明所有代码对象或全局变量的来源。

当前规则绑定一次原始 six 模块、导入器和注册表。删除并重新加载 six 本身，或在别名状态下重新加载目标模块，需要另行审查完整生命周期；如果真实 SDK 使用这些行为，必须在接入前补齐，不能把它们直接算成上游故障。

distutils 的自定义别名加载器、原生库初始化与链接库检查、冻结代码和解释器认证，以及完整辅助程序、主进程和工作进程接入仍待完成。当前选定模块核验版本为 v3，继续使用源码读取器 v1、router v4 和 context v3。
