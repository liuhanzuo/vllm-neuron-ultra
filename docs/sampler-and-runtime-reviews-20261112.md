# vLLM-Neuron 采样导入修复与三路运行准备

这轮确认并提供了一个 vLLM-Neuron 0.5.3 的单行修复：显式设置 `NEURON_ON_DEVICE_SAMPLING_DISABLED=1` 时，模型加载器把 Python 模块当作类调用，抛出 `TypeError: 'module' object is not callable`。同时完成 LFM 设备执行代码、MiniCPM5 诊断入口和 Spark 依赖清单的独立源码验证。当前 LFM 全量 CPU 实验继续运行；本轮没有新增推理提速，[提速总表](model-speedups-20261112.md)中的基线、精度及验证范围保持不变。

## vLLM-Neuron 0.5.3：特定采样开关触发模块调用错误

在固定上游提交 `f9ba933e9591e3cef163740516b1977aa1100493` 中，`neuronx_distributed_model_loader.py` 使用：

```python
from vllm.v1.sample import sampler as Sampler
```

这里得到的是 `sampler` 模块。`NeuronCausalLM` 在上述环境变量为 `1` 时执行 `Sampler()`，因此失败。对应 vLLM 0.16 源码的 `sample/__init__.py` 为空，真正的类定义在 `sampler.py`。修复为：

```python
from vllm.v1.sample.sampler import Sampler
```

[补丁与使用说明](../patches/vllm-neuron-0.5.3/README.md)已经保存。六项回归测试执行完整的原版及候选加载器源码，以替身隔离依赖，并保留 Python 实际导入语义：原版触发错误、修复后成功构造类，默认及显式设备采样分支均通过。测试没有直接替换加载器的 `Sampler` 名称。上游已有测试的自动 fixture 恰好将该名称替换为可调用 Mock，因此未能发现这个错误。补丁在原始 checkout 的 `git apply --check` 通过。

这个结论只覆盖固定源码和特定环境变量。当前模型 runner 正确导入类，并通过 `on_device_sampling_config` 选择 CPU 采样，不能由此推断通常的 CPU 路径均失败。此前 Qwen r6 API 启动失败的根异常仍未知，尚未证明与此问题有关。尚未执行补丁的原生导入、ABI、模型或 HTTP 验证。

统一实验分支的旧栈加载器已经使用正确的类导入。因此本次发布针对 0.5.3 的独立补丁和可复跑的复现材料，没有改动当前正在运行的 editable 环境。

## LFM3：具体设备执行代码通过 51 项独立检查

新增具体设备上下文、串行 worker、外层控制器、SDK 文件核对与完整 CPU 前置验证。主任务独立运行 51 项标准库／模拟测试，全部通过，并重新核对 616 个源码摘要，完整保留原 r2 的 595 项。

计划仍包含 91 个子任务、113 张图、3,491 项检查，保留 BF16／FP32、无效和重复槽位、输入不变、持久状态 alias、请求复用及全部原始矩阵。第一张设备图为 BF16 `(4, 7168)`。源码测试验证了失败时保留串行锁直到进程排空，以及启动时 `/usr/bin/env` 正常转换为 Python 的同进程身份检查。

实际设备启动还要求当前 CPU r2 的全部 874 个子任务、完整科学结果、真实外层退出与现场排空通过。候选首个 regression 阶段现已完整完成：123 批／1,648 例。主任务用原科学验证器逐批复核全部报告，核对原输入及参考输出摘要、输出逐字节一致和输入不变，并确认每个子进程的启动身份、实际退出 0 与进程结束，全部通过。[完整独立审计](evidence/lfm-candidate-regression-20261112/manifest.json)已保存。剩余 2,068 例 extended 阶段仍在运行，整个 r2 尚未结束。原、新环境各 3,716 例数据及三路控制的完整结果见[上一轮记录](editable-source-and-runtime-entry-20261112.md)。

SDK 清单涵盖 171 个安装包、39,825 个不含 pyc 的文件，声明约 4.954 GB。未来每个新子进程完整核对一次，91 次累计声明读取约 450.8 GB；实际页缓存、耗时与新编译器峰值尚未测量。设备阶段有独立的 16 GiB 内存、无 swap、24 GiB 输出及有限时间预算。已准备的清单不代表原生文件已经认证或设备已经编译。LFM 的 4096 上下文目标、完整模型与配对 HTTP 检查仍待完成。

## MiniCPM5：修复诊断入口的计时误判

这是自有诊断工具的问题。旧 guard 先读取剩余计时器，再读取当前时间，严格比较两者；哪怕正常经过 1 微秒，也可能误报 deadline 变化。主任务用旧 fixture 实际复现，并保留失败记录，未将旧 71 项固定时钟测试作为验收依据。

后继在设置及读取计时器前后采样单调时钟，纳入微秒分辨率误差。第一次设置预留 50 毫秒提前量，之后只收紧原到期区间，保留原 900 秒绝对上限及失败后持续拒绝的行为。若设置耗时超出预留量，直接失败。

主任务独立复跑 77 项检查全部通过，覆盖自然时钟推进、系统调用耗时、超时重设、完整 worker 成功与失败路径。完整 worker 测试执行实际 `source_entry` 函数体，外部依赖使用模拟接口；原九份 native 来源、1,284 份科学数据计划及原资源限制保留。有限分辨率无法证明“从未设置过完全相同的到期时间”，文档不作此保证。

Python 3.10 SDK 的解释器、`_ctypes`、`libffi` 的签名来源，以及真实动态加载与运行绑定仍待完成。这一结果不能作为 MiniCPM5 数值问题已修复或模型已加速的证据。

## Spark：依赖清单重建通过，实际库加载待检查

主任务独立运行 31 项测试，并用冻结 provider 重建清单，核对 178 份安装记录与 2,798 个源码摘要。清单声明 41,173 个文件、约 13.247 GB；原 4,844 条模型诊断事件保持不变。
