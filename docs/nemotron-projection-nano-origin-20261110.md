2026-11-10 UTC。本次完成两项进展：Nemotron 9B 的投影切分修复在六个长度上通过算子检查；Nano 4B 的模块来源检查增加了对标准库 typing 注册对象的明确支持。没有新增整模型提速结果。

## Nemotron 9B：六个长度上的原始／候选配对

输入为 BF16 `[1,T,11328]`，原切分尺寸为 `[5120,6144,64]`；候选保持数据类型和计算含义，以 `tensor_split` 明确使用边界 `[5120,11264]`。每种长度、每个版本均进行两组输入下的三个输出比较。

| 128 | 0/6 | 6/6 | 1,143/1,152 | 0 |
| 256 | 0/6 | 6/6 | 2,295/2,304 | 0 |

所有原始对照均通过 CPU 检查和编译，但设备输出错误。例如第一个输出的坐标 `[0,1,0]` 应读取输入偏移 11328，却读取了 5120；这与切分后未保留原行步幅一致。候选的 36 次输出比较全部逐位一致，各长度的抽查地址也全部正确，输入均保持不变。

12 个阶段均正常退出。对于原始对照，这表示成功复现预期错误；其内层 `primitive_passed=false` 和 `device_exact=false` 才是计算结果，不能把外层成功退出写成数值正确。六组原始失败记录和首个失败张量的路径、哈希、大小均保留；本次汇总只读取结果元数据，没有重新读取原始张量。

这验证了当前固定软件环境、batch=1 下的该投影消费者。它尚不代表整模型冷缓存 4096、长解码、并发、槽位复用、生成质量或 HTTP 性能通过。原 52 阶段实验仍在运行；失败对照不能作为提速分母。缺陷目前定位到已复现的 Neuron 转换路径，尚未独立归因到某个上游组件或其他版本。

## Nano 4B：让来源检查正确处理 typing 类入口

先前缓存检查发现，Python 3.10／3.12 的标准库会将 `typing.io`、`typing.re` 类对象注册到模块表。旧 `ModuleOriginAudit v3` 假设所有非空条目都是模块对象，会误拒绝这两个正常入口。

新后继 v4 在原来源检查基础上识别这两个确切对象，并要求额外回调明确认证其所属 typing 源码／代码和对象身份。每次检查都会重新调用认证；缺少回调、拒绝、返回非布尔真值或之后撤回认证，都会失败。对象替换、导出变化及未知类入口仍被拒绝；一般模块元数据转换规则不能放过类入口的变化。

两个原始 Python 环境各通过 26 项测试，共 52 次成功执行，覆盖原有 16 项场景和新增 10 项兼容及失败场景。测试实际使用 typing 类对象和生成源码导入，但认证回调是明确的测试替身，没有证明原环境 typing 源码已完成认证，也未执行 SDK 或模型。测试保留 `-B -S`，分别使用独立空缓存目录。

后续仍需把完整源码／原生库认证回调、v4 检查、独立缓存目录及解释器检查接入真实主进程、rank 和辅助进程的启动计划。此次没有修改正在运行的 Nemotron 源码或已冻结的 v3。
