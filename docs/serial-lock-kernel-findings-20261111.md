# 串行锁重复记录：对应内核源码与受控模拟

本次查明了一种可以产生重复锁记录的读取机制，并修正了 MiniCPM5 原生结果校验器的两个边界问题。没有新增整模型通过或提速倍数；已有结果仍见[提速总表](multi-model.md#existing-results-and-provenance)。

## 为什么锁表可能重复

本机运行 `6.8.0-1046-aws`，版本签名为 `Ubuntu 6.8.0-1046.49~22.04.1-aws 6.8.12`。从 Canonical 官方仓库取得对应发布标签，并核对标签和提交 `1ce040e1942e54c0ca2a835effd5d1aba8cf2e5e` 下的三份文件完全一致。这里只核对官方 HTTPS 来源及安装版本对应关系，没有验证 PGP 签名或重建内核二进制。

对应源码显示，`/proc/locks` 每一轮迭代期间受到锁保护，但两次底层读取之间不保持完整快照。第一次读到当前末尾后，下一次读取仍会按保存的序号，从可能已经变化的列表重新定位。Python 的 `read(2 MiB + 1)` 可以包含多次底层读取，内容不足一页也不例外。

用真实 Python 文本缓冲层和内存模拟的列表迭代器做了六项检查，独立复核全部通过：

1. 初始列表只有 29 项，末尾第 28、29 项为 A、B。
2. 第一次读取返回这 29 项；随后在它们之前插入两项新记录。
3. 第二次按旧位置继续读取，旧 A、B 变成第 30、31 项，再次返回。
4. 拼接结果末尾为 A、B、A、B，而每个时刻列表中都只有一份 A 和 B。

模拟的三次底层读取分别返回 1,480、112、0 字节，总共 1,592 字节，小于一页。它解释了为什么“内容很短”不能保证一次快照，也说明此前只切换一个独立锁的实验未必能复现需要两项净新增记录的情形。

这是源码支持且已模拟验证的可能机制。Dory 原失败没有保存底层读取边界和并发变化过程，因此历史实际原因仍未证实，原 exit 1 保留。不能把这项发现写成 Linux、Neuron 或模型仓库已确认的缺陷。

## 下一步怎样检查持锁状态

对应内核的 `/proc/<pid>/fdinfo/<fd>` 会找到该描述符对应的文件打开实例，并在文件自身的锁保护下列出关联锁；它比全局列表序号更直接。因此准备一个独立的新检查版本：绑定父进程身份、原锁文件、实际保留的描述符和完整独占锁范围，并在读取前后检查身份稳定。

全局锁表继续完整保留。缺失、冲突、格式异常或描述符证据不完整均拒绝；只有描述符证明成立时，才可能按新规则接受仅序号不同的同义重复记录。父进程必须一直保留锁至子进程全部退出，子进程不继承该描述符。单次 fdinfo 观察本身不能证明持续持有，新的检查仍需源码审查、负向测试和具体运行接入。旧检查及原失败记录不修改。

## MiniCPM5 原生校验器修正

独立复核发现两处问题：目录实际占用未计入容量上限；JSON 中的 `1e999` 会转为无穷大，绕过只拦截非标准常量的检查。新版本将目录计入原有上限，并拒绝数值溢出。22 项内存测试及额外独立检查通过，936 份原始输出、72 份逐步日志、官方缓存逐字节对照和原资源上限保持不变。
