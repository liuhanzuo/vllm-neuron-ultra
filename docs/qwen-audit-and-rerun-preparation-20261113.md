## 为什么要修复审计工具

原审计在每次 guard 检查中都重新扫描全部历史 handoff 文件。完整历史和源码核验会调用 guard 很多次，因此目录扫描被大量重复。源码确认了这一额外开销，但尚未测出它占本次总耗时的比例。

后继 v5 保留每次原锁检查，完整 handoff 扫描改为在 guard 调用时检查是否已到 0.5 秒间隔，并在关键边界强制扫描。检查的是原 ACK 中的完整路径和文件身份。首次检查、历史解析、报告收集、每轮完整物理清理检查的开始与结束、最后源码核验和每次结果发布前后，都有完整检查。阻塞操作期间不承诺硬实时的 0.5 秒检查频率。

全部历史、874 个相关子任务、完整源码与输入身份、报告和产物读取、原两轮完整物理检查均保留。主任务独立复跑 51 项源码／模拟测试通过，重新核对 657 项 Python 源码摘要，其中 654 项继承来源不变。模拟中减少了重复扫描，但这不是设备或整模型性能结果；实际审计耗时还需在下一轮测量。

独立复核曾拒绝 v4：脚本从包内迁到单文件后，仍使用旧目录层级，会把结果写到错误位置；此外，它只在两轮物理检查的整体前后强制扫描，没有覆盖每一轮的边界。v5 修正了这两项，补上真实源码位置与恒定时钟下的边界反例测试。v4 和拒绝记录保留，没有用于实际审计。

## 后续整模型验证准备

下一轮 writer 的请求与归档工具已完成独立源码复核，并通过主任务复跑的 11 项检查。成功归档必须额外核对独立审计器的资格文件，将它与实际退出、完整报告和源码清单精确绑定；失败路径不能出现资格文件。此前缺少该核对的草稿保留为拒绝版本。最终请求构造器固定上一轮请求的精确摘要，只能在真实退出审计及归档完成后生成新请求。目前没有生成实际 r3 请求或归档。

MiniCPM5 的精确 writer 来源生成器通过主任务 10 项独立源码／模拟检查。它只在收到真实完成的 catalog、退出审计和 finalization 后，生成七份待审源码；新增许可限于已确认的 35 个 writer 源文件和三个外部 root helper，保留全部 164 行历史前缀。原 SDK worker、数据重建、600/605 秒 CPU、900 秒运行墙钟、9 项原生检查与 1,284 项采集保持。若 r3 先执行，还必须依据其真实结束记录追加精确来源；该生成器不会接纳未知的 r3 helper。实际生成、完整准备预算与模型运行仍待完成。

整模型 writer 对照的现有草稿包含 28 个阶段：两侧分别新建 12 张图、使用相同 sampler，执行原数值、冷缓存、1,541 步长解码、槽位复用、203 个向量、采样对照、quality96 和匹配 HTTP。两侧各 124 请求、30,848 输出 token，要求 96 条质量文本与 57 对贪心文本一致。主任务重新核对全部 52 个交付成员和干净的 writer 提交 `e44408483a6880baa775d236d393812dedb2a443`。这些是待运行代码，尚未取得整模型资格。

源码核查确认两个实际接入缺口：旧双路径扫描器拒绝编译器的相对常量链接与固定 SDK 资源链接；最终扫描异常时，旧 outer 可能丢失终态记录。后继正在移植已审核的独立包 v8 修复，保留全部科学与服务退出要求。r10 大 JSON 的精确读取兼容已经存在，无需重做；原严格服务停止判定也保留。
