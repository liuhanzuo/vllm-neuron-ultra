# Nemotron 切分对照完成与 Nano 启动流程接入

2026-11-10 UTC：Nemotron 9B 的 32 个切分阶段全部结束，16 个候选形状的 96/96 次设备比较逐位一致，随后整模型编译阶段的服务启动超时，整模型验证未通过。Nano 4B 的日志修复接入及辅助程序启动顺序修复共通过 74 次测试。上述结果尚未构成新的整模型提速。

## Nemotron：修复是否真的覆盖跨行问题

两类消费者各测试八种形状：batch 1、长度 128/256/512/1024/2048/4096，以及 batch 4、长度 1 和 batch 1、长度 1。每种形状分别运行原方式与候选，每阶段有六次设备输出比较。

| 消费者 | 候选通过形状 | 候选逐位比较 | 原方式通过形状 | 原方式逐位比较 |
|---|---:|---:|---:|---:|
| 投影切分 | 8/8 | 48/48 | 1/8 | 6/48 |
| 卷积切分 | 8/8 | 48/48 | 1/8 | 6/48 |
| 合计 | 16/16 | 96/96 | 2/16 | 12/96 |

两个原方式的通过项都是 batch 1、长度 1。将 batch 增为 4，即使长度仍为 1，原方式也失败，候选继续通过；这与长序列结果共同支持跨行步幅错误的判断。卷积 batch 4、长度 1 的首个错误中，输出坐标 [1,0,0,0] 应读输入偏移 6144，原转换却读取 5120；抽查 36 个地址中有 27 个错位，候选为零。

候选保留 BF16 输入、原尺寸和消费者，仅明确切分边界：投影为 [5120,11264]，卷积为 [5120,5632]。全部候选输入均未改变，抽查地址映射均正确。

32 个阶段的成功退出包含 14 个成功复现错误的原方式对照，不能写成“32 个数值测试全部通过”。原方式的 14 个跨行失败不具备提速分母资格。这里的 96 次是算子比较，不能等同于整模型推理、冷缓存或质量验证，也尚不足以独立归因至某个上游组件或其他版本。

整模型编译阶段的服务启动于 04:10:28 UTC，阶段于 04:12:35 UTC 以非零状态结束。子进程未在 60 秒期限内从工作进程参数切换为预期的 vLLM 服务参数；诊断报 Post-exec observation deadline，最后仍为 --server-child，未捕获可接受的服务参数样本，服务日志为 0 字节。子进程随后由清理流程终止（returncode=-15，cleanup_only=true），不能将这一终止记为成功运行。

现有证据只能定位到服务启动切换超时，尚未证明 vLLM 已启动、整模型编译完成或编译器算术失败。准备与认证路径具体耗时还需测量；不能仅凭空日志断言原因。后续仍需原计划的状态复制、数值、冷缓存至 4096、长解码、请求槽位复用、生成质量、真实 HTTP 四并发与配对性能。切分汇总读取阶段 JSON；它不能替代整次独立原始张量与产物审计。

失败释放现已完成：外部实验实际退出码为 1，独立失败释放流程实际退出码为 0；53 个服务及进程组均已核对清空，三个 canonical 状态文件保持不变，队列已恢复。原失败审计保留，恢复审计明确保持失败，不升级为模型通过。

## Nano：日志修复已经接到工作进程

SDK 辅助进程现在通过后继 helper v2 使用监督器 v3；native worker v4 选择这个 helper，并保留原科学函数、模型、精度和运行要求。辅助程序的完整监督记录先写入文件，再判断输出是否完整以及执行是否成功。因此，握手前失败时已经产生的错误字节可以进入工作进程的失败证据。

进程组结果适配器新增 v3 支持，核对每路 EOF、截断、超时和“输出完整”字段的一致性。成功结果必须具有完整、未截断的输出，同时仍满足原来的身份记录先于放行、子进程实际退出和进程组清空要求。旧结果格式继续交给原适配器处理；原始记录保留，不只保存摘要。

14 项接入测试在两套 Python 中全部通过，共 28 次成功执行，包括两个实际生成的 rank 进程及各自 helper、正常完成、握手前后 helper 失败、失败证据保留、伪造输出完整标志被拒绝，以及原科学函数 AST 不变检查。科学计算、启动来源与资源检查使用测试替身；没有执行实际模型或 SDK。

初次 Python 3.12 测试有一项失败：新版正确保存了旧收据源码的 SyntaxWarning 和故障标记，测试却只预期故障标记。现已逐字节核对“原警告＋标记”，未抑制警告或修改冻结源码；初轮输出和源码快照保留。

## Nano：修正辅助程序参数切换的顺序

继续接入时发现，旧 helper entry v2 先把 Python 参数切换成安装的辅助程序，再进入导入上下文。但启动恢复策略需要核对包装进程的原始参数，因此二者直接组合会被拒绝。新回归测试已复现该冲突。

helper entry v3 先在父进程放行后进入真实调用方提供的启动上下文，再临时使用辅助程序参数执行原有受限源码入口，最后恢复包装进程参数后退出启动上下文。整个执行期间保持同一套来源检查。完成记录必须确认启动上下文正常结束，异常和非零退出继续传播。

新增 DeferredParticipantStartup 把来源策略的构造推迟到父进程放行之后，避免为准备策略而在放行前读取原生库。它要求原绑定参数、同一缓存与检查器，只允许一次启动。来源构造器仍由后续真实引导入口提供，不能把这个工厂视为完整来源认证。

这部分 23 项测试在两套 Python 中全部通过，共 46 次成功执行，覆盖旧顺序冲突、正确顺序、异常后的参数恢复、未完成上下文、放行前拒绝和缓存不匹配。启动与来源认证为明确标记的生成测试，没有运行原安装 site、SDK 或模型。
