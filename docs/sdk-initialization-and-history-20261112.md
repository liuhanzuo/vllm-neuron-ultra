`torch.classes` 是 PyTorch 创建的虚拟命名空间。固定的 `torch/_classes.py` 将其 `__file__` 设为相对占位值 `_classes.py`；我们的检查器把它按当前工作目录解析，误判成来自环境外的模块。这是预检来源检查的问题，尚无证据表明加载了外来 PyTorch 代码。后继需要核对原工厂源码、实际对象类型及命名空间身份；不能简单忽略所有 `torch.*` 来源。

该后继 native v6／serial v5 已完成源码复核，主任务独立复跑 51 项 worker 和 21 项串行检查通过。它复用研究路径已有的检查器，只识别 `torch.ops` 与 `torch.classes` 两个精确对象，并核对三份原定义源码、实际类及方法；其他模块保持原来源检查。Mini 第四轮现已结束并清理，Qwen 第四轮正在绑定完整 149 条历史记录；尚不能据此宣布包预检通过。

此前两次失败及完整记录表示修复见[前两轮记录](qwen-package-r1-and-mini-wire-20261112.md)。第三轮保留失败状态；研究适配器的 [r10 完整配对结果](qwen35-r10-results-20261112.md)不能自动转为独立包资格。

## SDK trace 的环境恢复错误

缓存槽位写入实验还发现两项问题。首先，SDK 导入会增加日志、XLA 和 Neuron 环境变量，旧实验驱动却在导入后仍要求环境与启动时完全相同，因此会拒绝正常初始化。

其次，本机安装的 `torch_neuronx/contexts.py` 使用 `os.environ.update(key=value)` 恢复环境。它写入的是字面变量名 `key`，没有恢复原来的变量。原 `trace` 默认通过 CPU 执行图构建，暂时把 `PJRT_DEVICE` 从 `NEURON` 改为 `CPU`；上下文退出后可能留下 `PJRT_DEVICE=CPU` 和 `key=NEURON`。使用固定 SDK 的实际 Python 函数体，在正常和异常退出两条路径都复现了这一点。这个复现没有启动模型或设备，不能作为实际 trace 完成的证据。

新的实验驱动保留原启动环境、图构建参数和设备实验：初始化后逐值核对十项固定默认变量，以及一个有限的插件开关分支，此后检查完整环境不再变化。只在原 SDK 的两个嵌套 trace 上下文内修正环境恢复，退出时恢复真正的变量名；未知变化、CPU 设置残留和字面 `key` 残留都会失败。修复仅在该实验进程内安装，未修改已安装 SDK 文件。

主任务独立复跑 33 项源码／模拟测试通过，包括真实 SDK 函数体复现、正常和异常恢复、环境漂移拒绝以及实际实验驱动接线。原八种布局、32 张图、46,368 次调用和全部资源限制保持。设备运行、实际预算与性能仍待验证。

也纠正此前测试范围的一处表述：旧 v2 测试为了替换历史查询接口间接导入了 `ctypes`，因此“完全没有原生模块导入”的笼统说法不准确；没有执行模型、设备或锁操作。新测试明确模拟该接口，并禁止 `ctypes` 和 SDK 模块导入。原记录保留。

## MiniCPM5 的历史源码兼容修复

Mini 上次配置准备因新完成 Qwen 记录中的 70 份仓库源码被旧路径规则拒绝。新入口只接受这 70 个固定路径与原始哈希，并核对两个真实失败退出记录及完整源码清单；准备阶段和运行阶段使用相同规则。完整历史、原失败状态、普通 JSON 的 8 MiB 限制和原 79,008 字节运行记录预算均保留。

十项源码／模拟回归通过；主任务另使用真实历史记录读取器成功核对全部 70 份源码，独立审阅还覆盖了六组负例。后继的 18 份 SDK 辅助 Python 源码已经包含在原继承集合，不需要扩大路径许可。

随后第四轮配置准备实际退出 0（session `33007`／terminal `3fce1f`），完整保留 148 条历史记录与 48,169 项源码。13 份产物、165 项启动源码和完整依赖引用已由主任务与独立审阅者核对；外层使用新入口 v7，SDK worker 与 37,178 字节启动源码保持不变。完整输入包加预留为 8,488,011 字节，低于原 16 MiB 上限。两份原生来源策略仅重新绑定完整源码映射哈希，原动态库规则和证据未变。

真实第四轮 session `95781` 最终退出 1（terminal `270de1`），外层 PID 为 `855446`。唯一运行产物 `admission.json` 为 43,273 字节，已经满足原 79,008 字节预算；失败发生在外层认证，SDK 子进程与观察器尚未启动。

这次是实验入口的序列化问题：已完成的源码观察包含两处七整数 `tuple`，构建 admission 时直接深拷贝保留了类型。写成 JSON 再读回后，两处变为 `list`，使原始完整字典相等检查返回 false。该条件是 `and` 表达式第一项，后面的摘要和当前进程比较没有求值，不能把失败归因于那些检查。用实际 admission 和完整启动源码重建这两处类型后，重新编码逐字节等于真实文件，原构造器及认证路径的模拟也复现了同一失败。

主任务独立复跑最小复现通过，并核对实际 launcher 的 `Popen.wait()` 返回 1；随后两次观察均确认原进程已退出、目标服务未启动且递归进程组为空，原串行锁可重新取得并释放。完整历史新增第 149 条失败记录。下一版只在记录边界规范化这两处序列；另已发现完整 37 KiB 启动源码会超过旧观察器 2 KiB 进程身份预算，须用经认证的无损表示完成接入后再重试。后者是后续源码问题，不是本轮失败原因。

这两处后继修复现已完成源码复核：outer v8 只把上述两处七整数序列投影为 JSON 列表，保留原观察对象与原始完整相等检查。进程身份在内存中仍保留完整 PID、启动时刻、命令行和进程组；只有精确匹配固定启动源码与参数布局时，才按无损编码后的大小执行原 2 KiB 预算检查。未知长命令、错误摘要、额外字段与身份变化仍会被拒绝。原等待、系统调用观察及清理方法保持不变。Python 3.12 和 3.10 各 15 项源码／模拟检查通过，主任务另独立复跑 15 项通过，包括实际失败文件及完整入口到模拟子进程的回归。尚未运行新的 Mini SDK 进程或模型。

本轮源码与实际退出证据见[完整清单](evidence/sdk-initialization-and-history-20261112/manifest.json)。原 15 个模型家族、原权重与精度要求、数值门槛、冷缓存、长解码、槽位复用、quality96 和匹配 HTTP 仍保留。
