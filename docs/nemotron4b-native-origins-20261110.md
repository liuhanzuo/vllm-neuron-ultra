# Nano 4B：原生库来源与加载失败检查

本轮为 Nano 4B 的真实 SDK 接入补齐了一组原生库核验组件，30 项模拟检查通过。它能在加载前核对指定文件，并在加载成功或失败后检查仍留在进程中的库。尚未执行真实 SDK 或模型，因此没有新增提速倍数，也没有把 Nano 4B 标为完成。

## 补上的检查

Python 包可以继续加载本地共享库。只核对 Python 源码不足以说明最终用了哪些库；初始化抛出错误，也不代表已经加载的库会全部退出进程。

| 环节 | 本轮行为 |
| --- | --- |
| 读取原生文件之前 | 必须先通过调用方提供的实验队列和资源检查，再按原路径、文件身份、长度与 SHA-256 核验；读文件期间继续检查资源条件 |
| 加载前后 | 核对有执行权限的文件映射，以及名称为共享库的只读或读写映射；设备与 inode 必须与已核验文件一致 |
| 初始化失败 | 仍检查残留映射。出现未登记的库时停止导入，不能当成普通可选依赖缺失继续运行 |
| 正常可选依赖缺失 | 核验正常时保留原 ImportError，允许 Python 原有的可选依赖回退 |
| 导入描述变化 | 固定实际选中的 spec 对象、原始加载器与检查包装器，拒绝额外修改名称、来源、搜索路径或更换对象 |

检查同时拒绝已删除文件的映射、未登记的匿名可执行页，以及含有歧义的映射路径。Linux 会把文件名里的换行显示成 `\012`，这与文件名中原有的同一字面文字无法区分；这里直接拒绝这种路径，不猜测对应哪个文件。

## 实际检查了什么

30 项检查使用临时生成的字节文件和 Python 模拟加载器。导入流程走实际 CPython 与现有 router v4，但替换了原生加载器的方法，不会调用系统加载器去执行 SDK 共享库。检查覆盖完整哈希、文件替换、可观察的文件信息变化、描述符关闭、失败后的残留映射、原异常与退出值保留，以及导入描述修改。

另外重新核对了此前 47 个标准库扩展和 4 个 SDK 依赖候选的文件信息。当前观察进程的映射补入 7 个不同的解释器或系统库文件，合计 58 个候选。这里只读取路径、文件信息和映射记录，没有显式打开或重新计算这些候选库的内容哈希；它们还不是已批准的真实 SDK 完整依赖清单。

初次测试记录也已保留：测试最初期待 RuntimeError，而公共检查函数实际抛出 ValueError；另有两项快速同长度写入没有产生可观察的文件信息变化。修正后的测试明确改变时间字段，以验证能够观察到的修改。这个修正没有消除下面列出的并发写入限制。

## 为什么暂缓 distutils 分支

当前辅助程序的静态依赖图有 267 个可达 Python 模块、2,446 条导入边和 856 条未解析边界。两组边里都没有发现 setuptools、distutils 或 pkg_resources 的导入目标或导入者，安装源码目录表里也没有这些模块。

这不能证明运行时不会动态导入它们。我们保留该兼容边界，先推进实际接入需要的原生库检查；不能把此前对加载器行为的研究写成已发生的上游仓库故障。

## 尚未覆盖的部分

文件哈希证明的是读取当时获得的字节，后续文件信息相同不等于内容永远不变。并发原地写入如果没有改变观察到的文件信息，可能绕过后续元数据检查；实际运行仍需要排除并发修改。

内存映射核验也不是逐字节的内存测量。加载后的快照能发现仍然存在的未知映射，但不能阻止依赖库的初始化代码已经执行，也不能发现加载后又卸载的短暂映射。因此它不是安全隔离机制，真实运行前仍须完成链接依赖、动态加载路径、解释器与冻结代码、预加载模块、主进程和工作进程的具体接入。若 SDK 需要额外的匿名可执行页，也须按实际行为检查。

Dory r3 保存结果复核在本轮观察时仍运行，原有七项 FP32 检查失败尚未解释。后续串行次序保持为：实际复核完成并汇总、清理已授权的已完成存储、Nemotron 9B 后续实验、MiniCPM5 保存探针分析。冷缓存、长解码、请求槽位复用、生成质量与 HTTP C4 的要求继续保留。
