# LFM3 的 4096 验证补充与新栈接入

本轮补齐了 LFM3 自身 4096 缓存形状的设备测试代码，并开始在独立 vLLM-Neuron 0.5.3 checkout 中实施模型插件迁移。当前 CPU r2 的候选首阶段 1,648 例已通过独立审计，扩展 2,068 例仍在执行。本轮没有新增设备、整模型或提速资格；[提速总表](model-speedups-20261112.md)保留原有实测范围。

## 4096 检查为何需要补充

旧设备矩阵中的 4096 长度案例来自 RNJ，每个 rank 有四个 KV 头；LFM3 每个 rank 只有两个 KV 头。两者编译形状不同，不能用 RNJ 的成功替代 LFM3。

新的追加矩阵使用 `(B, 2, 4096, 128)`，覆盖 B4、B8、B16。独立写入包含单行、部分行与满批输入，共八张图；持久状态测试为每个容量各一张 reference 和 candidate 图，共六张。它们核对完整输出字节、输入不变、设备实际持有的 K/V 状态以及绑定是否保留。

| 检查范围 | 子任务 | 图 | 检查项 |
|---|---:|---:|---:|
| 原完整矩阵，全部保留 | 91 | 113 | 3,491 |
| 新增 LFM 4096 独立写入 | 8 | 8 | 543 |
| 新增 LFM 4096 持久状态 | 6 | 6 | 270 |
| 合计 | 105 | 127 | 4,304 |

新增序列覆盖 2047/2048、4094/4095，保留重复、乱序、无效和复用槽位，并加入完整 signed-int64 越界控制。读取缓存时，无效读取索引暂用零；写入器仍收到原始 int64 槽位，必须拒绝无效目标写入。reference 与 candidate 使用相同初始状态及输入。这个局部测试不等于完整模型已连续生成 4096 tokens。

主任务独立复跑 16 项源码／模拟检查，通过全部原任务保留、完整新矩阵、缺项及错误拒绝、成对输入一致、真实退出记录接线等检查；重新核对全部 622 个源码摘要，原 616 项保持不变。原串行锁、进程身份、SDK 认证、资源上限和完整 CPU 前置条件均保留。测试没有导入原生栈或操作设备。

真实执行仍需当前 CPU r2 完整结束、全部 874 个子任务与外层真实退出通过并排空。新增检查也不能替代完整模型的冷缓存、长解码、70 个状态的生命周期、槽位隔离、quality96 和配对 HTTP 对照。

## 新栈迁移保留模型计算，明确接口边界

主任务重建了 43 个文本文件、68 段源码证据及 16 项 API 比较，结果与交付材料完全一致。其中 14 个完整函数 AST 相同、15 个签名相同。旧数学计算、TP 分片与扁平状态接口有可复用基础；这仍不证明 Torch ABI、编译或服务行为已经兼容。

LFM3 的 24 层包含 13 个卷积层、6 个完整注意力层和5个滑动注意力层。每个 rank 有 13 个卷积状态、22 个 K/V 状态，共35个；TP2共70个。它们与新通用 runner 为所有层生成的 `FullAttentionSpec` 并非同一种内存描述。

迁移将单组 contiguous cache 明确作为调度器的请求槽位代理：B 个真实 Neuron 槽位、B+1 个调度块（含 null block），实际混合状态另有完整账本。代理数值不能报告为真实 HBM 消耗。抢占恢复、prefix caching、块式 KV 搬运等未实现功能必须显式拒绝，不能仅凭更新 block IDs 就宣称支持。

在 `/home/ubuntu/src/vllm-neuron-ultra-sdk053-lfm3-20261112` 中，已从固定上游提交 `f9ba933e9591e3cef163740516b1977aa1100493` 建立独立分支，正在实现 opt-in 注册、独立版本和产物身份、新 NKI writer 接线、专属编译产物检查，以及新版 `execute_model`/`sample_tokens` 两阶段中的 CPU sampler hook。当前安装及实验环境未替换；迁移代码尚未发布为可用模型版本。

2048/4096 与 B4/B8/B16 是各自待验证的配置，旧速度和产物验收不能转移到新软件身份。新栈仍需独立完成原数学、冷缓存、长解码、请求复用、质量和性能门槛。

## Spark：原生文件预检代码通过独立复核

新的串行预检保留 41,173 个载荷文件、1,271 个 ELF 候选及15处安装记录冲突。未来运行时会完整计算文件摘要，再通过同一文件描述符读取有限 ELF 元数据；不执行目标库或加载模型权重。文件与 ELF 的请求读取总量保持原16 GiB上限，超出支持范围、读取失败或摘要不符会明确记为未解决。

主任务独立运行44项检查通过，核对2801个源码摘要，并确认11个原锁、启动确认和排空机制的 AST 不变。完整42,459行模拟事件的读回与篡改拒绝检查通过。这些是源码及模拟结果，尚未执行实际原生文件预检。

补充元数据观察发现，15个冲突文件的当前大小全部与选用的 OpenCV headless 4.11 声明一致，包括 `cv2.abi3.so` 的66,106,617字节；未选用的4.13声明为69,729,273字节。大小一致不代表内容已认证，更不能证明加载器选择正确，因此未卸载或覆盖任何包。

独立依赖重建还确认：生成器主动选择的 `transformers[torch]` 引入了缺失的 `accelerate`。去掉这个生成器选项的分析结果仍保留相同178个已安装包，仅移除该缺失节点。已审查的直接诊断路径不调用 `from_pretrained`、`device_map` 或 offload，并有相应可选依赖守卫；当前没有依据安装 `accelerate`。完整动态导入闭包仍待实际核验，原清单保持冻结。
