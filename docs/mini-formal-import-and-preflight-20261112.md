## MiniCPM5 实际发生了什么

正式配置通过完整准备和具体内容复核：48,057 条源码映射，8,403,457 字节的完整 map，以及分开的 outer／SDK 来源策略。第一次绑定保留 143 条已结束实验；失败记录纳入后，第二次绑定保留 144 条。原始文件、失败现场和准备草稿均保留。

| 尝试 | 实际退出 | 失败位置 | 已确认的范围 |
|---|---|---|---|
| formal r1，session 47649 | 1 | 继承的 `LD_LIBRARY_PATH=/usr/local/lib:/usr/lib` 被原外层检查拒绝 | 发生在 SDK 子进程启动前；未创建输出目录。未及时观察到该次外层完整进程身份，记录明确保留这一限制。 |
| formal r2，session 85296 | 1 | 写 `admission.json` 时超过原 79,008 字节联合运行元数据上限 | 已独立观察真实外层命令和清理后的加载器环境；执行到准入记录写入，输出目录为空。未构造 SDK adapter 或启动 SDK 子进程。 |

第一轮修正只清理外层继承的三个动态库加载变量，没有降低校验标准。第二轮暴露了正式入口接线与原记录预算的兼容问题；失败记录没有保存完整待写入字节，因此暂不声称测得了它的精确大小。正在检查新增字段和重复信息的表示方式，保留原 79,008 字节上限及所有完整来源、进程身份和科学验证要求。

两次工具真实退出后均独立检查了进程清理、活动任务和原串行锁。原九项原生检查的完整诊断、1,284 行科学实验以及模型数值、冷缓存、长解码、槽位复用、quality96 和匹配 HTTP 验证仍待完成。外层走过某些来源核验，不能代替整个诊断成功。

## Qwen 独立包预检的串行接入

已将接受的原生预检 v3 接到现有锁、完整历史检查、服务监控和子进程清理逻辑。独立复核发现 v1 的一个失败处理缺陷：如果服务还未安装就启动失败，清理虽已证明没有进程，后续检查仍要求服务存在，会无限持锁等待。

v2 对这个分支重新使用原有“从未加载、无捕获身份、进程组为空”的检查；已安装服务仍走原身份与退出验证。18 项源码／模拟检查和 6 项独立检查通过，覆盖延迟安装、实际失败码保留及已捕获身份消失拒绝。原 v1、共用运行器和原生预检 v3 均未修改。

这是源码和接线验收。真实 package 导入、spawn、完整分词输入对照、配置往返及小张量检查仍需在最新串行目录下执行；它们尚未完成，更没有独立包模型提速结论。
