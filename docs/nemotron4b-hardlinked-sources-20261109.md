# Nano4B：保留原文件的硬链接源码读取

上一轮发现，本机 distutils 和 lib2to3 的 112 份源码使用硬链接，而原读取器只接受链接数为 1 的文件。本轮用独立的新版本修复了这个兼容问题，接入导入器、动态导入上下文、模块核验和辅助程序启动测试。

选定版本为读取器 v1、router v4、context v3、module origin audit v2。五组共 104 项检查通过；随后使用新版逐一读取现有来源清单中的 1,023 个真实源码模块，共 16,248,589 字节，全部与记录的指纹和文件身份匹配，包含 112 份硬链接源码和两个明确记录的符号链接。

源码验证没有导入这些包，也没有运行真实 SDK、模型或性能测试。因此，本轮没有新增基线合格结论或提速倍数。

## 具体改动

有多个硬链接的源码，必须同时提供明确的原始链接数和完整文件身份记录。读取器在打开文件前、打开后及读取完成后检查身份，并核验完整字节数与 SHA256。只接受有记录的 Python 源码，不允许把原生库或模型文件传给这个读取入口。

原有符号链接规则继续保留：先核验明确记录的一跳链接，再读取原目标源码，模块仍显示原路径。源码文件没有被重新链接、复制覆盖、删除或去重。

导入器的源码文本接口同时改用 Python 标准的编码识别，保留源码声明的编码。初次编码测试漏了按需加载的 encodings.latin_1，导致一个测试失败；后续测试明确核验该标准库源码，没有预加载编码模块来绕过检查，原失败记录已保存。

## 验证覆盖

| 检查组 | 通过数 | 主要证据 |
| --- | ---: | --- |
| 源码读取 | 10 | 通过另一个硬链接修改内容、读取中新增链接、替换文件身份、错误指纹、异常时关闭文件 |
| 导入器 | 38 | 实际硬链接模块及包的相对导入、链接数量变化、符号链接、源码编码、可选依赖回退 |
| 动态导入上下文 | 22 | 保留原导入器对象和顺序、动态注册、重新加载、来源拒绝 |
| 已加载模块核验 | 16 | 模块替换、元数据变化、缓存注入、明确授权的别名与原生入口 |
| 父进程放行及启动集成 | 18 | 模拟辅助程序实际导入硬链接源码，原文件与另一链接保留同一 inode 和原链接数 |

五组测试都使用明确的测试策略，不构成真实 SDK 授权。全部实际启动的测试子进程已经回收。此前固定版本的 14 个源码指纹重新核验未变。

真实源码读取另有独立结果：每个模块记录路径、字节数、指纹、原始链接数和链接信息，读取过程中检查文件身份；没有调用查找器或加载器去执行被检查源码。这证明新读取器能处理本机完整的当前源码清单，不能代替实际运行和数值正确性验证。
