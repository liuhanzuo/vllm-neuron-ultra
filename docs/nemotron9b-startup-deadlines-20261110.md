# Nemotron 9B：启动前校验实测与分段期限修复

原 v24 整模型复验在服务子进程启动阶段失败。父进程给“完整准备校验 + 切换到模型服务”合用 60 秒，但独立串行诊断测得，**原封不动的完整准备校验单独耗时 66.144 秒**。因此当前的启动期限存在实际不足；这一轮尚未证明整模型能够启动或正确推理，也没有新增提速。

## 实测是什么

诊断使用原 vLLM-Neuron Python 3.10 环境、CPU 0–7、nice 10，直接调用冻结的 `nemotron9b_package_protocol_v24.bundle`，保留原执行规格、源文件和历史检查。没有执行模型、服务或编译器。全部完成，外部进程退出码 0，运行者已消失，串行锁已释放，三份规范状态文件未变。

| 测量 | 墙钟时间 | CPU 时间 | 用途 |
| --- | ---: | ---: | --- |
| 第一次，未开启逐行跟踪 | 66.144 秒 | 66.089 秒 | 本次环境下原完整准备校验的实测总时间 |
| 第二次，开启逐行跟踪 | 128.976 秒 | 128.840 秒 | 定位校验开销所在步骤，不能作生产耗时或性能分母 |

跟踪轮中，`sources(s)` 所在行累计 102.995 秒，历史注意力完成记录验证所在行累计 19.702 秒；编译器资产哈希验证所在行仅 0.0145 秒。逐行跟踪明显增加了开销，**103 秒不是未跟踪情况下的源校验耗时**。

整个诊断用时 205.840 秒，执行 832 次资源检查，重新核对 1,202 个历史服务和 398 个历史运行者。没有重置文件系统缓存，也没有复现原父进程的编译阶段 guard 负载；本次只计时 bundle，不含其后的服务身份和健康检查。它支持“60 秒不足”的修复方向，但不能追溯证明先前被终止的子进程恰好卡在哪一行。

## 修复候选

保持原完整校验，拆分三个有界期限：

1. 准备阶段最多 300 秒，等待原子写入且通过父子身份绑定验证的执行意图。原子标记仍由子进程在 bundle、父子进程身份、服务身份和健康检查之后写入。
2. 验证执行意图后，单独给予 60 秒完成服务命令切换。PID、启动时间、父 PID、cgroup 和目标命令必须仍然符合原约束。
3. 实际切换被观察到以后，独立控制器的确认重新计时 60 秒。原代码复用了最初的 60 秒期限。

空命令行只保留原有的 0.25 秒短暂容忍，准备阶段首次观察到的空命令行时间会带入下一阶段，不能借阶段切换延长。异常、取消、身份变化、准备超时和确认超时均继续拒绝，pidfd 绑定的进程清理路径不变。

300 秒是依据本次测量选择的有限准备预算，并非所有后续环境都能在此范围内通过的保证。

## 验证与实际状态

新候选通过 23 项合成计时、身份和 worker 控制流程测试；原执行切换的 15 项回归测试也在后继辅助函数上通过，共 **38 项**。其中直接调用候选 worker 的 HTTP 控制流程，在模拟 67 秒准备、53 秒切换、50 秒独立确认后完成；另一例验证准备超时仍调用原清理路径并保留失败原因。模型与 HTTP 服务均由测试替身代替，不能视为真机服务通过。

AST 对比确认，worker 除 `http_stage` 外的函数与 v24 相同，包括子进程完整准备校验、科学计算、输入准备和结果门槛。修复仍是**源代码候选**，入口明确拒绝直接启动；尚需接入完整后继协议、源文件清单、最新已完成任务历史和新的串行实验规格，再做真机复验。未改动或重启已释放的 v24 r10。

原结果继续保留：候选 16 个形状共 96/96 次逐位一致；原实现只有两个 B1T1 阳性对照通过，共 12/96，另外 14 个跨行形状失败。失败对照不能用作提速分母。完整模型仍须通过冷缓存至 4096、长解码、槽位复用、生成/RNG/停止/文本/质量、真实 HTTP C4 和配对性能检查。
