测量使用已冻结 builder v2 的 530 个本地 Python 文件闭包，并合并 Nemotron r12 与 MiniCPM5 已完成实验的全部来源映射。所有文本逐份完整认证，没有抽样，没有丢弃历史来源。文件打开时累计的文件大小不等于物理磁盘读取量；上表文本字节是认证函数实际返回的完整文本大小。

检查在原性能观察锁内执行，保持 CPU 6、nice 19、1 GiB 地址空间、120 秒 CPU、180 秒墙钟及单文件 1 MiB 限制。20 份历史原始载荷、九个业务原生库、模型和张量读取均为零。Python 自带 `_ctypes`、`_decimal` 初始化是明确记录的标准库例外；模型 SDK 导入、业务库加载、进程创建和业务 ctypes 调用仍被拒绝。

前三次测量分别被检查工具的标准库初始化限制与 `INSTALLER` 文本文件类型限制阻断。失败记录完整保留。第四版只为真实分类中的确切文本路径补充允许范围，并取消错误报告对源码行的隐式读取，最终实际退出 0。没有据此认定冻结源码存在不兼容。

该测量不覆盖后继 builder v3/v4、审核程序修正，也没有调用生产配置生成、真实前序排空、原生库认证或模型运行。完整生产准入的时间和资源仍需实测。

## 审阅发现：历史退出证据不能只比较名字和数量

新增实际审核退出记录程序的初步 26 项检查通过，但独立审阅又构造了五类本应拒绝却被接受的记录：整批或单个单位缺失采样、资源组仍有进程、单位名与属性 Id 不一致，以及仍有待执行任务。旧读取器只在 `samples` 字段存在时核对它，并把服务名和属性 Id 合并成集合，因此遗漏了这些情况。

进一步读取真实旧代码发现，历史证据有不同格式：部分任务保留双采样，部分只保留一次属性／资源组观察，还有部分只保存资源组摘要；较老的属性格式没有 `Job` 字段。不能把这些旧记录补写成“当时已经检查”的证据。

后继修正保留完整旧记录，计划在实际审核取得原串行锁之后，进行两次完整前序观察，并对缺少任务状态或只有资源组摘要的单位补充当时实际读取的属性和空资源组证据。两份完整观察必须稳定一致；缺失、非空或不匹配记录均拒绝。原 2 GiB 内存、600 秒 CPU、900 秒墙钟、解压后 32 MiB 和最终单文件 2 MiB 限制保持不变，超限必须停止。后继严格证据校验器 27 项、独立审核器 34 项、审核实际退出记录器 26 项、完整配置生成器 12 项源码／合成检查已通过。真实旧记录的只读解析覆盖 1,261 个单位，其中 1,255 个需要补充缺失状态；这不是新一次物理排空。实际执行和容量边界仍待验证。记录器与配置生成器的独立 38 项复查通过，原先五种错误接受的变异全部被拒绝；544 个本地文件的完整源码依赖已核对。

## 模型结论与下一步

Nemotron r12 已独立核对至少 37/52 个阶段的成功结果、保留的实际退出和进程排空，原会话继续运行。整模型编译、数值、冷缓存、长解码、请求槽位复用、质量与真实 HTTP 配对性能仍需完成。现有基线 NaN 问题未据此解决，没有新提速分母。

MiniCPM5 下一轮仍要等待 Nemotron 的真实终止和独立释放记录。此前 180 次 attention 调用的结果不变：同时使用官方当前输入和有效历史，局部汇总相对 L2 从 1.2720% 降到 0.4464%，但没有完全匹配的帧。整模型原对照数值 29/32、首选 token 32/32，两个候选数值各 28/32、31/32，仍不合格。

全部 15 个模型家族、原权重与精度、原完整验收门槛继续保留。本轮没有新增模型提速倍数。
