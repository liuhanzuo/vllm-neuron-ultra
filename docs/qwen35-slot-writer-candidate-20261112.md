# Qwen3.5 下一项候选：合并解码槽位写入

最新实测：[首轮设备测试在原实现的第一次特殊 BF16 值检查处失败](qwen-slot-first-device-result-20261112.md)。原实现与候选两张图已编译；候选正确性与计时尚未执行。完整输出摘要与负零／NaN 规范化的重建结果一致，具体发生层仍待诊断；原严格门槛保留。

源码检查定位了一项可以单独比较的设备端优化：复用已有的 NKI 条件写入器，合并 Qwen3.5 B4 解码中四次完整缓存选择。**目前是待测候选，没有 Qwen 实测提速。**

原函数按四个更新行依次执行 `torch.where`。现有 NKI 内核先确定每个目的槽位最后匹配的更新行，再输出一份完整缓存；重复槽位保留最后一次写入，未使用槽位保留原数据。该内核仍读取旧值和更新值、写出完整结果，不能称为零复制或只写一个 token。

每个 TP rank 包含以下状态：

| 状态 | 数量 | 单个张量形状 | 精度 |
|---|---:|---|---|
| 卷积历史 | 18 | `[4, 3072, 4]` | BF16 |
| 循环状态 | 18 | `[4, 8, 128, 128]` | FP32 |
| 完整 KV 缓存 | 12 | `[4, 1, 4096, 256]` | BF16 |

KV 写入实际使用当前解码桶的前缀。按源码中间结果的大小计算，TP2 每个 B4 步骤可能少产生约 244–802 MiB 的选择结果。这个数字不是实测 HBM 流量：编译器可能已经融合原操作，实际收益必须由配对计时决定。

候选保留单行 prefill、缓存读取、KV 前后段拼接、注意力与 GDN 算术，以及原 BF16／FP32 策略。LFM3 已验证的同类写入优化说明值得测试，但其提速不能套到 Qwen，也不能与 CPU sampler 的倍数直接相乘。

下一步为全部八种 Qwen 精确布局做原始实现与候选的字节比较、持久状态别名检查和配对计时。正确性覆盖 B4 槽位域 `{-1, 0, 1, 2, 3}` 的全部 625 种映射，包括重复、部分活动和全部未使用槽位；计时使用固定的代表性映射。原语诊断源码已冻结并通过独立复核，尚未编译或执行。16 项作者源码／模拟检查通过；独立检查覆盖 34 个调用案例，26 种故障均被拒绝，包括“输出正确但持久状态未更新”。完整计划为 32 张图、46,368 次调用，含正确性、重置、预热和计时；这些是计划量与模拟调度计数。

源码接入还有一处细节：已有 tensor-split 修正会复制函数的全局变量，因此写入器必须在复制之前绑定，或显式注入复制后的函数；主进程和 spawn 子进程都要核对实际调用目标。即使原语测试通过，仍需重新完成整模型数值、冷缓存、长解码、槽位复用、quality96 和配对 HTTP 验证。
