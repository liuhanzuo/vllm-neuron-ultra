# DeepSeek：核对真实权重加载与布局变换

DeepSeek-R1-0528-Qwen3-8B 的关闭／开启采集对照需要确认两侧使用相同的原权重，并理解设备如何解释分片。新增权重加载观察组件已完成源码审查，**18 项隔离测试通过**，主任务核对了 15 份源码和说明的完整哈希与文件身份。当前尚未接入真实运行，没有加载权重、编译或读取设备张量，也没有新增模型提速倍数。

这次源码核对明确了三个不同阶段：

| 阶段 | 实际行为 | 能得出的结论 |
|---|---|---|
| 编译捕获图 | 原调用为 `trace(initialize_model_weights=False)` | 不能在这个阶段取得实际已加载分片的值 |
| 加载模型 | 原 `shard_checkpoint()` 生成两个 rank 的分片，交给 `nxd_model.initialize` | 可以观察真正送入初始化的全部分片，而无需另算一套参考分片 |
| 初始化权重 | 可选 `LayoutTransformation` 转换权重，再交给全部桶图 | 还需核对实际变换和图的权重绑定；名称、形状相同不充分 |

新组件在原加载方法内部记录布局变换前的完整两 rank 分片，以及初始化后的完整权重 CPU 表示。每个键记录 dtype、shape、stride、存储信息、完整字节数和 SHA256；原分片和加载方法各调用一次，返回原对象，异常或结束后恢复方法。读取字节使用等宽字节视图，没有数值转换，标量缓冲也完整保留。

CPU 表示来自 `detach().cpu().contiguous()`，不能称为设备物理存储的直接转储。因此，即使两侧记录相同，也只报告分片值／CPU 表示相同；设备布局语义、图的权重接口和整模型验证仍未通过。观察可能额外复制一个完整张量到主机，真实接口支持与内存峰值尚待实测。两个对照的 **47,150,344,192 字节**原始输出预算保持，另需计算编译、缓存及加载峰值。

固定 SDK 源码还保留两项限制：`model_builder.py` 的 TODO 指出推理 metaneff 的权重形状可能尚未随布局变换更新；`hlo_utils.py` 的 CPU WLO helper 前有“CPU 与设备 WLO 不一致”的 TODO，其支持的变换形式也有限。本次未重现该不一致，不能将注释当作本模型的已证实故障，也不能把该 CPU helper 直接当作正确参考。

DeepSeek 专用序列化检查器现已完成源码复核，**16 项合成归档测试通过**。它先验证外部指定的整个模型归档 SHA256 和文件身份，再复用原惰性解析器读取布局变换的完整 NEFF、metaneff、序列化标记、rank 数及全部 12 桶的实际权重输入位置，并记录所有保存代码的完整摘要。大型 NEFF 和图定义按块读取；未知 pickle 类型、扩展注册表绕过、尾随内容与超限输入均被拒绝。没有读取真实模型产物。

检查器分别报告布局变换、逐位置权重接口和保存代码是否完全相同；任何差异都原样保留。保存代码可能因采集功能而合法地不同，此时“严格相同”路线不成立，不能据此判定数值不等价。即使这些保存组件相同，仍不能单独证明真实加载值、C++ 运行时的权重解释或完整设备布局；需与加载观察、实际绑定及原始数据对照共同验证。[8 项检查器源码与审查证据](evidence/deepseek-weight-descriptor-20261113/manifest.json)保留这些范围限制。

审查同时纠正了自有工具的调用说明：观察组件会导入 SDK，不能直接包在现有设备入口外，否则会触发入口原有的“新进程尚未导入原生库”检查。v2 要求后继入口先完成这项检查，再在实际加载边界安装观察；该接线尚未完成。v1 错误示例与修正记录均保留。串行入口在缺少可用布局证据时应于开始昂贵阶段前拒绝启动。

18 项测试使用模拟张量与 SDK，覆盖完整字节、两个 rank、标量缓冲、值变化、重复加载拒绝、回调失败和方法恢复。它们不证明实际设备支持这些接口。后续仍保留完整 126 帧 logits、9,072 份 KV、144 个状态与原 14 个失败帧的复现和采集中立性比较，以及 2,041 步长解码、93 个检查位置、槽位复用、quality96 和匹配 HTTP。
