# MiniCPM5：保存张量数值分析的串行执行器

MiniCPM5 两种候选改动在现有严格 CPU 检查中仍被拒绝：通过帧数从对照的 29/32 降到 28/32，首选 token 一致帧数从 32/32 降到 31/32。下一步要利用已保存的中间张量，观察哪些帧、哪些阶段的差异最大，再决定后续改动。

本轮已把前序任务核验、资源检查、原有读取器和数值报告核心接成一个串行执行程序，并准备了在前序任务实际结束后生成运行方案的工具。51 项检查全部通过。真实张量分析尚未启动，因此本轮没有新增模型正确性结论或提速倍数。

## 将分析什么

沿用[已核验的输入与读取器](minicpm5-saved-tap-io-20261109.md)和[完整数值报告核心](minicpm5-saved-tap-report-20261109.md)，没有重跑模型或被拒绝的候选。

| 内容 | 完整范围 |
|---|---|
| 原始元数据 | 95 份 JSON，27,711,882 字节 |
| 已保存张量 | 84 份 BF16 文件，3,145,728 字节 |
| 比较方案 | 严格 CPU 对照与两种候选，以及两种候选之间的比较 |
| 轨迹 | 每组全部 32 帧，保留原有物理行排列 |
| 数值位置 | 第 0 层和第 41 层的注意力输出、整层输出，共 4 处 |
| 向量比较 | 3 组比较 × 32 帧 × 4 处 = 384 项 |
| 双分片 | 两份副本都读取并核验字节相同，统计只计一次 |

报告中的差值和后段/前段比值只用于描述变化。它们不代替原始 FP32 终点判定；严格 CPU 对照本身尚有失败，不能把相对它的差值称为绝对 HF 误差，也不能仅凭比值证明因果关系。其他 209 个记录位置没有保存数值，仍只能使用既有指纹信息。

## 如何接入现有队列

实际执行前，程序必须取得原串行锁，核验完整源码、真实退出凭证及完整任务历史，确认全部记录中的进程和服务都已结束，然后才能读取原始张量。

支持现有两条前序链：Dory 审查直接成功后使用 Nemotron v22；若 Dory 审查实际失败并完成规定的重试，则使用 Nemotron v23。它会保留既有 1,149 个服务记录，并追加 Nemotron 的控制服务和全部 52 个阶段（包含最终原始数据审查），合计 1,202 个服务。进程身份来自实际记录，不推测缺失的启动时间。

前一模型失败也可以继续推进其他模型，但必须同时保留原始非零退出和另一条实际成功执行的内置失败释放记录。失败状态、未启动阶段和原始审查结果都会保留；失败控制组不能充当提速分母。自定义恢复程序或缺少真实身份、退出记录的情况需要新的完整历史适配，当前实现不会把它们跳过。

当前 Dory 审查仍在运行。实际顺序继续保持 Dory → 已授权的有限存储维护 → Nemotron → 本项保存数据分析。源码准备没有插入新的串行任务，也没有提前生成真实运行方案。

## 执行和失败处理

这是一项 CPU 诊断任务，固定使用一个 CPU 核、2 GiB 地址空间上限和 30 分钟时限，保留原定磁盘及可用内存下限。读取过程中每次都检查串行所有权、运行窗口、资源与服务状态；复用已准备的独立服务查询连接，不减少检查频率，也不缓存旧状态。

输入严格绑定原始文件及目录身份、大小和完整内容指纹。输出写入全新的目录，每份文件只能写一次，并进行同步写盘；即使同步写盘失败，已尝试写入的大小仍计入预算。读取、数值检查、状态复核或服务查询清理任一失败，都不会写出成功结果。程序自己的结果也不会宣称已证明自身退出，最终还需要从外部记录真实退出。

## 本轮验证到哪里

- 20 项前序完成检查：覆盖两条 Dory 分支、完整阶段和资源约束、真实退出、原始审查，以及显式失败释放与失败状态保留。
- 17 项运行约束和输出检查：覆盖完整输入与 384 项比较、不得改变原始判定、文件覆盖、目录替换、大小上限和写盘失败。
- 8 项完整执行流程检查：覆盖成功顺序、前序或输入失败时禁止读取张量、数值分析失败、部分报告、状态变化、清理失败和释放串行锁。
- 6 项方案生成检查：缺少实际前序完成时停止、两条分支的输入保留、指纹冲突、执行程序缺失、目录复用和失败释放凭证绑定。

这些测试使用生成数据或模拟执行流程，不是实际新一轮模型或原始张量运行。另外完成了真实的源码和文件属性检查：404 份本地 Python 源码、4,851,679 字节；36 个既有源码指纹未变；全部 179 个输入文件及目录身份仍与原清单一致。原始张量仅检查属性，没有读取内容；也没有加载服务查询的原生库。
