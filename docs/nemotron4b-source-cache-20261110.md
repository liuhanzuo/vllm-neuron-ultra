# Nano4B：排除启动字节码缓存，并兼容 typing 的注册方式

2026-11-10 UTC：新增 `EmptyBytecodeCache`，准备在后续 Nano4B 启动中使用独立空缓存目录。当前工作仅验证启动源码的加载方式，没有执行真实 SDK、原生参考计算或 Neuron 模型，也没有新增提速倍数。

## 为什么只用 -B 不够

Python 的 `-B` 选项禁止写入字节码缓存，但仍可读取已有的 `.pyc`。在加载已准备的 Nano4B 工作程序源码后，实际观察到以下候选路径：

| 原始环境 | 已加载的源码模块数 | 对应缓存文件存在的数量 |
|---|---:|---:|
| Python 3.12 原生参考环境 | 99 | 92 |
| Python 3.10 Neuron 环境 | 96 | 89 |

这些统计只表示缓存文件存在，没有判定实际缓存是否过期，也没有逐一证明它们被读取。单独的生成文件实验复现了问题：在缓存时间戳和源码长度仍相符时，`-B -S` 会读到旧内容，即使源码文本已变化。

## 新的启动检查

候选启动参数保留 `-B -S`，增加每个参与进程独立的 `-X pycache_prefix=...`。父进程需预先建立属于当前用户、权限为 0700 的空目录，并记录其完整身份。检查模块要求目录身份不变、始终为空，实际解释器参数匹配，并逐一核对普通源码加载器的缓存路径都落在该目录中。

生成文件实验确认，此时读取的是当前源码，原有缓存文件保留，私有目录没有产生新缓存。两套真实解释器加载准备好的工作程序源码也成功：Python 3.12 的 100 个、Python 3.10 的 97 个源码模块均通过缓存路径检查。数量各增加一个，包含新检查模块本身。

这一步覆盖缓存排除。源码内容、解释器、冻结代码、原生库及完整运行依赖仍须分别验证。

## 期间修复的兼容问题

首次对实际工作程序源码做检查时，两套环境均失败。原因在我们的检查代码：它假设模块表中所有非空对象都是模块。实际标准库把 `typing.io` 和 `typing.re` 两个类对象也注册在模块表中；Python 3.10 使用普通 metaclass，Python 3.12 使用 `typing._DeprecatedType`。

现已核对这两个对象与原 typing 入口的身份、类字段、版本对应的类型及导出对象。未知对象、替换的别名和改变的导出仍被拒绝。这里兼容的是 Python 的正常行为，没有改动标准库。两次初始失败、对应源码和原始输出均保留。

## 验证与剩余工作

当前版本在两个解释器中各通过 15 项测试，共 30 次成功执行。另有两次实际源码观察成功；原环境的 site 启动钩子、Torch、Neuron SDK、模型与原生库内容均未执行或显式读取。生成测试中的旧缓存不能当成原环境缓存有误的证据。

新的启动参数必须接入后继主进程、两个 rank 及各自辅助程序的具体启动计划，每个进程分别绑定自己的目录。现有 `ModuleOriginAudit v3` 的元数据函数仍假设模块对象，完整来源检查还需明确兼容经过验证的 typing 类入口。当前源码缓存检查通过不能直接授予模型运行权限。

[源码、实际退出和观察记录](evidence/nemotron4b-source-cache-20261110/manifest.json)保留完整局部依赖和首次失败。[前序导入分发检查](nemotron4b-bootstrap-dispatch-20261110.md)继续负责原始分发函数的绑定。原模型精度、冷缓存至 4096、长解码、槽位复用、生成质量与真实 HTTP 配对性能要求全部保留。
