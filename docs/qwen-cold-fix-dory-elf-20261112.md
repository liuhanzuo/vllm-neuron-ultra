## Qwen：失败发生在哪里，修复改变了什么

第四轮的数值检查实际得到 32/32 个 argmax 一致，最低余弦相似度 0.9995153546、最大 KL 0.0024827272、最大绝对 logit 误差 0.375。主任务重新应用原元数据验证器确认通过；本轮还没有独立复核全部 203 份原始向量，因此不能把局部结果升级成完整模型验收。

冷缓存原入口自己调用 `frontend_split_correction_v2.install("qwen35")`。新的运行包装器在进入原入口前又调用了一次，严格安装器发现 `forward` 已被替换，立即拒绝。冷缓存的 84 帧计算、长解码、候选组及性能阶段均未完成。这是自有运行器的接入错误，证据不支持归因于 Qwen 模型或上游 Neuron 实现。

最小 leaf v2 仅让 `cold` 由原入口负责安装；状态复制、数值和长解码继续由包装器安装。原冷缓存函数整体不变，仅沿用原有的输出目录重定向。8 项独立检查用原安装器和完整原入口的 AST 复现旧版双重安装失败，并检查新版只安装一次；预先安装、坏缓存或缺少准入仍被拒绝。

随后发现两处清理问题：本机 systemd 支持的是 `--kill-who=all`；原运行器使用了不支持的拼写。其次，协调进程失败后，部分已结束的临时服务被回收，原外层没有接续其已保存的完整退出记录，进入持续持锁的错误恢复状态。主任务先独立检查所有已记录进程、21 个声明服务与空进程组，再终止精确匹配的外层进程。原工具最终退出 **137**，表示失败后的清理，不是模型成功；缺失的原 `outer-terminal.json` 和 `coordinator-result.json` 没有补造。

runtime v4 修正命令参数，并只在完整的阶段配置、进程身份、服务 invocation、原退出状态和两次空组记录都通过认证后，复用已保存的终止事实。复用前还要再次观察进程消失和服务组为空；失败状态仍为失败。缺记录、身份变化或未排空继续拒绝。原 44 项与新增 24 项检查独立通过，连同 leaf 的 8 项共 **76 项**。这些是源码与模拟检查，真实运行仍需重做。

第五轮已使用冻结 v4 源码启动。主任务独立重建并核对全部 117 条串行历史、47,929 项来源；真实外层随后完成两遍完整物理核验和正式准入，协调进程与原锁已独立确认，运行交接得到确认。工具会话为 `42713`，当前继续内部验证与原完整计算流程，尚没有第五轮模型或性能结论。

原 BF16 权重、FP32 循环状态、TP2/B4/context4096、12 个图、冷缓存 84 帧及 672 项清零检查、1,541 步长解码及 87 个检查点、槽位复用／隔离、203 份原始向量、13 项采样控制、quality96 与完整匹配 HTTP 均保留。

## MiniCPM5：修正收尾竞态，导入故障仍待诊断

v3 修复处理的是父进程两次观察之间子进程退出的竞态。仅在进程已经消失，或原身份保持而命令为空时，允许再次检查真实退出状态；仍在运行或身份改变一律拒绝。原 `wait`、完整子进程组排空和真实退出记录继续执行。18 项集成、4 项契约和 17 项竞态检查由主任务独立通过，正常化 AST 与冻结来源也已核对。

这不会修复此前 `libcusparseLt.so.0: failed to map segment from shared object`，也不会补造缺失的旧 SDK 子进程退出码。2 GiB 地址空间上限确实在导入前生效，但原因仍未证明。下一步单独记录原环境、原导入前流程、进程内存和完整异常，并保留原预算。库名出现 CUDA 组件不等于运行了 CUDA 推理。

独立 SDK 导入诊断的三份运行源码现已完成，主任务独立复跑 **60 项**纯检查通过；33 个导入前代码块与原流程核对一致。诊断保留原解释器、完整来源和输入描述认证、原 2 GiB 限制，只启动一个独立 SDK 子进程，不伪造前一科学阶段完成。它会记录有界内存状态及完整异常 frame／cause／context／errno；不额外读取源码行，不猜测缺失 errno。若原 guard 或磁盘拒绝落盘，明确报告真实退出记录未保存并保持失败。该结果只接受源码，实际导入诊断尚未运行。

原五阶段、4,392 份派生原始文件、1,752 条事件、前后 60 份原输出控制及 96 份整数参考全部保留。该诊断用于解释数值差异，不能代替模型或性能验收。

## Dory：实际依赖图与此前静态预览有何不同

r3 实际工具会话正常退出 0，读取 `torch/lib/libgomp.so.1`、`torch/lib/libtorch_global_deps.so` 和系统 `libgomp.so.1.0.0` 的固定内容，其余 24 份 ELF 使用已有认证元数据。没有启动目标解释器、导入框架或执行这些库。

真实元数据产生 **114 条依赖边、43 项未覆盖项**，区别于之前保存预览的 105 条／39 项；新增内容揭示了更多依赖，不应沿用预览数字。所有“实际选中库”字段仍为空，原 **15 条运行时加载关系**仍未解决。主任务从保存元数据独立重算图并完全匹配；这次独立检查没有再次读取原生二进制载荷。

计入预算的元数据实际共 33,351,985 字节，仍在原 32 MiB 限制内。结果中的 `metadata_bytes_read` 是最后一次 handoff 读取之前的快照，少计该次 93,129 字节；独立审计根据完整消费清单补明最终值。运行中的原计数器继续检查上限；旧 preflight 的额外元数据加载并不属于这个计数器，不能称之为进程全部读取量。

已通过包内容来源确认加载器为 Ubuntu `libc6 2.35-0ubuntu3.15 amd64`，但精确打补丁源码、实际 Build ID 与匹配调试信息尚未齐全。文件存在或出现在 maps 中，不能证明具体依赖请求最终返回了它。原 11 项导入也未必触发所有 CPU 变体、惰性扩展或可选路径。后续逐步取得精确来源与加载关系证据；Dory 的两轮计算、共 56 份独立注意力历史及 TP1 保持。

本轮还保留两次未完成尝试：r1 在创建输出前因根盘低于原保留线而退出；r2 因主任务在命令中误填摘要占位值被入口拒绝，连配置都未读取。二者均未产生模型计算结果。
