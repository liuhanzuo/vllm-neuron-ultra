# LFM 日志上限与 Qwen、MiniCPM5、Spark 后续准备

2026-11-12 继续原 15 个模型家族的工作。LFM 完整 CPU 对照在新环境测试数据生成阶段失败，现场和退出后核对已保存；本轮另完成官方模型记录复查、Qwen 后继配置工具、MiniCPM5 原生追踪接口的源码审阅，并重新推进 Spark-X2.6-4B 移植。没有新增整模型资格或推理提速，既有数字和适用范围见[各模型提速总表](model-speedups-20261112.md)。

## LFM：测试数据报告完成不等于进程成功退出

原 Python 3.10 环境的 3,716 个样例、291 个批次已经完成并独立核对。同一个运行随后在 Python 3.12 环境重新生成输入和预期输出，要求 dtype、shape、完整字节数及哈希逐项相同。新环境保存了 232 份完整报告、覆盖 2,968 个样例；但最后一个子进程退出码为 120，因此只有 231 个批次、2,967 个样例具有零退出记录。worker 同样退出 120，外层工具实际退出 1，控制与候选模拟器计算均未开始。

共享 `runtime.log` 恰好达到原 262,144 字节单文件上限，末尾是重复的 Python 3.12 `invalid escape sequence` 语法告警。完整报告已写出而解释器最终返回 120，支持日志上限与退出时 flush 失败的解释；现场没有直接保存 EFBIG 或相应 flush traceback，不能把底层原因表述为已完全实证。后继日志修正 v3 已通过 26 项集成检查与 12 项告警专项检查的独立复跑，并经主任务源码审阅接受。它只处理四条精确匹配的告警：类别、文本、绝对路径、行号、完整源码哈希和源码行均须一致。worker 保留首次告警，各批次在原有 JSON 中保存完整签名和计数，其他告警和错误继续输出；原 592 个执行源码记录保留，新增三个，共 595 个，资源上限保持。

独立审阅另发现：如果警告收据自身验证失败，原失败 JSON 可能无法写出，但原异常仍在 Python 异常链中，真实非零退出仍会使任务失败。这是失败诊断完整性的限制，尚未在真实运行中发生；不能因缺少 JSON 而认定任务通过。告警计数仅覆盖实际送到 `showwarning` 的调用，不能代表默认过滤器已经隐藏的告警。

主任务独立重读 1,054 份 JSON，核对全部 523 份报告、启动确认、父进程记录的退出及新旧环境测试数据哈希。随后两次观察确认 outer、worker 和 523 个批次子进程全部退出，服务进程组为空，原串行锁可取得并已释放。报告的 `passed` 没有覆盖最后批次的真实非零退出。旧输出和已执行源码保持原样。

完整计划保持三遍各 3,716 个样例，加一个三组对照子进程，共 874 个子进程。本轮没有通过该完整计划。候选修正针对模拟器 BF16 写回；原模拟器失败记录保留，即使未来完整 CPU 检查通过，也不代表芯片行为、缓存别名、整模型或性能已经通过。

## Qwen：保留完整历史的后继配置准备

已审核的运行器 v6 需要新的配置才能接续完整实测。本轮增加有限准备工具，保留 r5 的全部 47,929 份源码摘要、117 条串行历史记录、36 个 spec 输入和 137 个 overlay 输入。工具必须显式接收之后实际完成的退出记录、交接记录、完整队列以及全新的输出路径；源码冲突或历史文件身份变化都会拒绝。

主任务独立运行 12 项检查通过，包括旧记录丢失或变化、重复源码冲突、历史文件身份被刷新、前置任务仍运行、候选覆盖历史，以及运行器拒绝未审核配置。准备工具测试中的未来记录为合成数据。LFM 实际退出后，已创建真实 r6 候选，完整保留原有输入和源码记录，包含 47,959 个源码摘要与 120 条串行历史。

独立重建发现两个自有准备工具问题：把已在基础计划中的 15 个相同输入再次加入 overlay；把 8,691,419 字节的旧 r5 配置当作受 8 MiB 限制的普通输入。新候选只去掉这些新增重复项，将旧配置及其身份留在准备来源记录中；原 36 个 spec 输入、137 个 overlay 输入、完整源码记录和原运行限制均保留。另一次审核进程误导入了不属于运行闭包的准备工具，被原加载检查拒绝，随后在干净审核进程中重做。旧候选与失败记录保留，未修改验证器。

真实 r6 的完整来源重建、历史执行来源核对、47,927 个文本源码与三个 Python 字节源码核验，以及正常 `Bundle` 构造和解析均已通过；九个原生库的实际认证由持有原串行锁的运行器执行。新配置保留 47,959 个全部类别的来源记录。r6 已通过实际准入，协调进程及运行 ACK 已逐项核对，主任务确认实际父进程和协调进程身份、原串行锁均一致。之后按原顺序进入原生预检和配对模型流程；截至本次运行确认尚无新的阶段结果。原生数值、冷缓存、长解码、槽位复用、quality96 和匹配 HTTP 流程保持。

## MiniCPM5：观察内存映射失败的原生接口准备

原 SDK 导入实际失败仍是 `libcusparseLt.so.0: failed to map segment from shared object`，没有取得对应系统调用 errno。既有纯事件逻辑之后，本轮增加延迟加载的原生接口和原输出存储类的窄适配，主任务独立执行 27 项纯模拟检查通过。

接口要求先由外部审核过的认证函数核对解释器、ctypes、libc 及其必要依赖，之后才允许导入 ctypes；加载后还须验证实际库提供方。当前没有可用于实际执行的完整认证凭据。保存记录表明原 Python 的 `_ctypes` 是内置模块，必须核对该解释器，不能用另一个 Python 环境的动态模块替代。现有 libc／loader 安装包重放证据可以复用，仍须核对完整证据链和当前文件身份。

追踪由原父进程完成。接口独占 SDK 子进程的 waitpid 所有权，非阻塞发送完整输入，只对已知任务收取真实事件；实际终结与整个拥有进程组排空后才能交回等待所有权。它不会将停止事件或 ECHILD 当作退出成功。GET_SYSCALL_INFO 超过缓冲区时拒绝解析，ptrace 只在失败时读取 errno。

新增追踪和退出记录计入原 8 MiB 元数据、32 MiB 实际分配及 79,008 字节运行元数据预算，原 2 GiB 地址空间与 900 秒期限保持。真正的原生来源核验、外层接线和 ptrace 执行仍未完成；模拟检查不能证明失败根因或实际追踪能在原期限内完成。

## Spark：混合注意力的移植源码

沿用固定官方版本 `aa074aa851209a683aeaf5f99a8e25a642d94541`，模型包含 4,112,079,360 个唯一参数、36 层、291 个状态键。此前完成的 meta／辅助 CPU 检查没有加载官方权重。本轮第一版源码以原 Python 3.10／NxDI 0.8／vLLM-Neuron 0.2.2+lts 环境为目标，拟定 TP2、容量 B4、context 4096。

移植保留 27 层窗口 512 的滑动注意力和 9 层全局注意力，分别使用 511 个历史位置的环形缓存及 4096 个绝对位置的缓存。解码先按时间顺序读历史，再加入当前 K/V；新请求 prefill 替换该槽位所有缓存单元。仅缓存本体每个 TP rank 为 415,014,912 字节，不含权重、激活、编译和运行时内存。

计算源码保留 FP32 残差和归一化、BF16 投影、GELU、各层不同的 RoPE，以及输出投影之前的逐头 sigmoid 门控。打包 QKV 先按 Q=4096、K=1024、V=1024 行拆分，再进行 TP2 分片，不能直接把整个打包矩阵对半切。第二版改为 SDK `GroupQueryAttention_QKV` 的单次打包投影，关闭尚未验证的融合内核。SDK 先分别切 Q/K/V，再拼接各 rank 的 Q2048/K512/V512；TP2 归约与 BF16 舍入仍可能带来数值差异，尚未执行真实张量对照。

主任务独立复跑 5,688 条标准库标量、索引、语法和入口断言通过，覆盖原缓存／掩码 oracle、跨 511 边界、不同请求长度、槽位排列和复用。这些断言没有执行 Torch、SDK、完整模型或芯片。第一版公共加载和服务入口主动拒绝执行，目前只能称为张量源码与 SDK 接入草案。

源码审阅进一步发现需要修正的自有接线问题：SDK 在转换权重前已去掉 `model.` 前缀；trace 固定传递七个位置参数，额外 `spark_*` 参数不会自动进入；SDK 输入转为 int32，索引操作需要明确类型处理；不足 B4 时填充的无效槽位不能写坏有效请求的缓存。第二版已依照固定 SDK 源码修正这些接口，加入 int32→long 索引、对原始槽位 ID 的掩码写入、host 历史位置检查、槽位复用，以及单 token prompt 的 `[1,0]` 补齐。

第二版独立复跑通过 1,607 项标量／AST／模拟断言与 21 项 host 模拟检查，其中含 209 种有效／无效槽位排列。主任务已完成四份实现源码和独立审阅证据复核，接受为源码进展。实际 Torch 执行、72 个缓存输出的别名行为、编译、长解码和 HTTP 仍待完成，入口保持未启用。逐槽位 `torch.where` 可能增加缓存流量，没有已测性能收益。继承的调试方法 `reset_kv_cache()` 不适配当前缓存字段；冷缓存验证必须采用独立设计的 fresh-load 流程，普通 reset 仅清除 host 记账。

SDK 的全局滑动缓存更新对各层采用同一个取模规则，因此仅配置每层容量不足以实现 Spark 的混合注意力。这是适配边界，不能据此认定 SDK 支持范围内的模型有缺陷。官方 1M 位置配置也不代表本机已验证 1M 上下文。

本轮对同一批 19 个官方发布方分别查询最新创建的最多 16 个仓库，共取得 293 条记录、19 次请求，全部成功。与 2026-11-11 的同范围记录比较，没有新增仓库或 SHA 变化。此查询是有限范围复查，不是全站搜索或发布日期证明；原 15 个模型家族、固定实验版本和权重精度均保持。
