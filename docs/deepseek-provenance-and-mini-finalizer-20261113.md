# DeepSeek 文件来源校验与 MiniCPM5 清理收尾失败

本轮补齐 DeepSeek 实验入口的两项缺口，并确认 MiniCPM5 清理收尾程序实际失败。没有新增模型提速倍数，也没有回收此前计划的 9.475 GiB 空间。完整原始权重、精度、冷缓存、长解码、请求槽位复用、quality96 和配对 HTTP 验收要求保持。

## DeepSeek：修复自有实验入口

第一版串行入口复用了 Qwen 的运行状态生成函数，导致在添加活跃任务时仍继承 `running=False`、`active_serial=None`。主任务用原函数的合成输入复现了这个矛盾。v2 使用 DeepSeek 专用生成与校验函数，明确记录运行状态、真实父进程和协调进程、工具会话，以及完整继承历史。阶段结束不能提前发布空闲状态。

第一版认证了编译产物和原诊断输入，但没有认证完整官方 checkpoint、配置、索引和分词器文件。v2 增加完整逻辑路径到物理文件的清单：根据外部固定摘要对每个物理文件完整读取一次，核对精确声明的软链接和硬链接关系，再由后续进程检查文件身份。共享文件保持共享；未知别名、缺失分片和超出允许范围的配置修改均拒绝。

作者的 **21 项隔离测试通过**。主任务审查了两项修复，并重新核对 **19 份新增源码、704 份继承源码和 1 份资产清单**的完整摘要与稳定文件身份；未重复运行已通过测试。服务与阶段实现和 v1 逐字节相同。此前拒绝记录与开发失败日志均保留。

这里认证的是原始文件来源。实际加载后的权重布局和图的权重接口仍需证明，所以入口继续在读取运行绑定、申请串行锁及启动昂贵阶段之前拒绝执行。没有运行七阶段完整对照，也没有验证 47,150,344,192 字节的双路径原始输出。另见[权重加载观察与序列化检查](deepseek-weight-load-20261113.md)：18 项观察组件测试和 16 项序列化检查器测试均属于工具验证。

## MiniCPM5：已完成重放，清理尚未完成

已完成的 2,352 对文件比对及完整重放保持有效：11,859 个逻辑输入、14 份报告和 98 份布局已核对，恢复后保留 169 条完整串行记录。这些成功工作不需要重跑。

之后的重复数据清理会话 `4693 / d5f983` 实际退出 1，发生在删除前；自有只读校验错误拒绝了一份已经允许共享的历史来源文件。独立收尾会话 `26060 / 64c33a` 随后也实际退出 1，触发原 7,200 秒限时，调用栈位于完整历史的物理状态核对，经历史元数据读取回调进入全局检查。旧运行没有分阶段耗时，不能断言两小时全花在该阶段，也不能据此断言尚未运行的 v4 必然失败。

已独立确认旧清理进程、收尾进程及最后的辅助进程均不存在，原串行锁可以取得并释放；完整保存了旧控制目录 10 个节点，其中 9 个 JSON 文件的字节和身份。旧删除日志、完成收据、新串行目录和空闲状态文件均不存在。**没有恢复删除，没有发布虚构完成状态，回收量为零。**

后续恢复使用独立目录，保留原失败和全部旧文件；需完成历史核对、两次全量原件／保留副本身份与已分配空间检查，再记录失败收尾。新恢复源码只属于后续审计，不能追溯归入已经退出的清理任务。恢复成功后才可创建新的清理轮次，真正释放空间后再推进 Qwen KV256 对照；原 40 GiB 启动门槛保持。

以上两类问题均来自自有实验流程，目前没有证据把它们归为 DeepSeek、MiniCPM5、Transformers 或 Trn1 芯片故障。
