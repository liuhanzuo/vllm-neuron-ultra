验证在独立缓存目录中进行，启动前通过命令行指定缓存位置，并关闭缓存写入和 site 初始化。启动所需的三个 encodings 源码事先核对了完整摘要；验证程序编译四份源文件，但不执行新生成的 code object，不读取待验缓存来执行其中代码。检查还覆盖完整的 16 字节文件头、时间戳、源码长度、编译路径、解释器版本、启动模块路径及前后文件身份。原模型环境和缓存均未改动。

第一轮解释器成功完成编译，但父程序因模块来源路径检查失败而退出 1：安装器提供的 `cpython-3.12-…` 别名指向已认证的 `cpython-3.12.16-…` 目录。后继仅加入这一条真实观测的精确链接，在子进程启动前和结束后核对目标及身份，编译仍使用原规范绝对路径，没有尝试多个路径挑选成功结果。第一轮失败与退出证据保留，属于自有检查工具的路径兼容问题。

第二轮真实任务 `28749` 退出 0（`9b090d`），4/4 文件完整匹配。独立复核真实退出 0（`ffb26e`），重新读取全部编译输出及当前源码、缓存，重建完整文件并逐字节比较。子进程组已排空，原串行锁随后释放。先前三个缓存比原始分发包多 43 字节的现象，不再构成无法解释的内容来源缺口；这里证明的是当前安装路径下的完整可复现性。

仍待确认的是 13 条 vLLM 依赖加载关系和 2 条 libgomp 选择关系。文件存在、摘要正确或 Python 缓存可复现，都不能单独证明实际进程选择了哪个动态库，也不能代替原生 ABI 或模型正确性测试。

MiniCPM5 方面，清理一个闲置编辑器版本及六个停用的软件版本实际释放 699,133,952 字节，未删除模型或实验数据。其准备与运行时历史校验各有一个 64 条记录上限，已不足以容纳完整历史；正在准备保持全部记录的后继。新的原生采集尚未启动。

原权重、BF16、冷缓存 4096、长解码、请求槽位复用、质量 96 和配对 HTTP 验收条件保持不变。已有实测倍数见[统一结果表](multi-model.md#existing-results-and-provenance)。本轮[证据清单](evidence/dory-python-caches-20261111/manifest.json)提供完整输出、编译结果、来源检查代码及实际退出记录。
