## 启动代码发生在脚本入口之前

本机 SDK 环境有两份包含执行语句的 .pth 文件：一份注册 vLLM-Neuron 的可编辑安装，另一份注册 setuptools 的 distutils 处理。正常启动 Python 时，它们先于我们的脚本入口执行。因此，单在脚本中等待父进程放行，尚不足以保证所有环境初始化都在放行之后发生。

生成的隔离样例复现了这个顺序，并验证了下一版启动设计：以 -S 暂缓 site 初始化，先完成真实父子进程身份握手，父进程允许后再调用 site.main。样例中，正常启动确实先执行 .pth；延后启动则在父进程放行之后执行；拒绝放行时不会执行。所有样例子进程都已回收，未生成字节码。

样例恢复了虚拟环境前缀，但 sys.flags.no_site 仍为 1。这一差异必须记录，真实辅助程序是否依赖该标志还没有验证。当前验证只使用临时生成的环境和启动代码，并未运行本机 SDK 的启动代码，也不构成真实辅助程序的运行许可。

## 本轮修正的是我们的核验脚本

第一次清单生成在检查旧环境源码时停止：读取器错误地要求每个文件只有一个硬链接，而原生参考环境已有 9 份安装源码或元数据使用 2～3 个硬链接。选定的分析器 v2 保留实际链接数量，仍要求完整内容与原始指纹一致；通过其他硬链接改写内容的测试会被拒绝。没有改动安装文件，早期源码和失败记录均保留。这不是模型、SDK 或其他仓库的计算故障。

25 项检查包括 18 项依赖清单检查、3 项原始源码与硬链接检查、4 项真实样例进程的启动顺序检查。覆盖摘要与大小不符、漏记源码、重复 RECORD、路径越界、符号链接、拒绝读取原生载荷、隐式父包、跨包相对导入、命名空间、动态导入边界，以及父进程拒绝放行。
