# MiniCPM5 长提示第 1 帧：固定完整 context 的输出投影对照

2026-11-08，固定原权重与完整输入的输出投影对照已完成。原生 1,231 token 输出及 CPU 两个 rank 的 2,048 行输出，三份控制均逐字节复现。对同一 CPU context 改用完整 BF16 投影后，与已保存原生输出不同的元素从 **802,431 / 2,521,088** 降到 **2,967 / 2,521,088**；仅把分片结果的求和加宽到 FP32，输出完全不变。

这是局部数值机制的实测进展，**没有新的整模型合格结果或提速倍数**。尚未把完整 BF16 投影接入整模型；此前 FP32 输出投影和全矩阵 down 候选的否决结论不变。

## 固定了什么

使用注意力 r3 已保存的真实 context 和投影输出，不重跑注意力或模型，不更换输入。原生 context 是 `[1,1231,2048]`；两个 CPU rank 各为 `[1,2048,1024]`，按原 rank/head 顺序组成 `[1,2048,2048]`。所有计算先作用于完整物理形状，再分别统计全体、有效前缀和末预测位置；不把末行单独拿出来计算。

从原 checkpoint 的准确区间读取完整 8 MiB BF16 输出权重 `[2048,2048]`，核对实际文件身份、文件头、完整矩阵哈希及两个 `[2048,1024]` 列分片哈希。原参数不变，所有分片和完整公式使用同一份权重数据。

运行使用既有 SDK 的 PyTorch `2.8.0+cu128`，计算全部在 CPU；原生形状控制用 2 个线程，CPU 形状控制用 1 个线程。原生模型使用的 2.9.1 解释器未重新运行，原生端点是在 SDK 解释器中按完整字节复现。两个分片在单进程重放求和，必须匹配此前真实 Gloo 的两个 rank 输出；本次没有重跑 Gloo。

## 六种完整形状对照

下表是不同 BF16 输出元素的数量，越少仅表示这两个局部输出更接近，不直接表示模型质量更好。

| 对照 | 原生 context，全部 1,231 token | CPU context，有效 1,231 token | CPU context，全部 2,048 行 |
|---|---:|---:|---:|
| BF16 分片投影 vs 完整 BF16 投影 | 802,189 | 802,174 | 1,442,630 |
| 仅把分片求和加宽到 FP32 vs 原 BF16 求和 | 0 | 0 | 0 |
| 完整 FP32 投影最后转 BF16 vs 完整 BF16 投影 | 853 | 843 | 1,669 |
| FP32 分片乘法/求和最后转 BF16 vs 完整 FP32 最后转 BF16 | 490 | 488 | 951 |
| FP32 局部乘法先各自舍入 BF16 再求和 vs 最后才舍入 | 802,206 | 802,189 | 1,442,643 |
| 局部 FP32 乘法先舍入再求和 vs 原 BF16 分片 | 246 | 240 | 495 |

原生 context 的两种 BF16 投影相差 802,189 个元素；CPU context 的有效前缀相差 802,174 个。末预测位置均相差 695 / 2,048 个元素。这些对照内部使用完全相同的输入，因此差异可归于被替换的投影计算路径，而不是这次对照的上游输入变化。

只加宽求和后差异为 0，说明事后加宽无法恢复已经舍入成 BF16 的局部结果。FP32 分片计算先各自转成 BF16 再求和，会重新产生大量差异，支持局部舍入是重要来源。它仍与原 BF16 分片路径有少量差异，FP32 分片与完整 FP32 也不完全相同，不能把所有差异都归为单一舍入操作。

原生与 CPU 的实际 context 仍有 28 个元素不同。保留 CPU context、只切换到完整 BF16 投影后，与原生输出的差异为 2,967 个，最大绝对差从 0.0078125 降到 0.00390625。该跨路径比较仍包含既有 context 差异和原物理长度差异，不能解释最终 logits 的全部 KL 误差，更不能代替整模型验证。

这里的 FP32 计算仅用于诊断；没有把模型精度改为 FP32，没有启用优化插件。

## 独立复核与资源

运行实际退出 0，约 43.67 秒，峰值内存 1,044,303,872 字节；计入依赖校验和数据读写，不是性能基准。保存了 12 份完整候选输出、两套 BF16/FP32 分片中间结果和原始完整投影矩阵。

退出后，独立标准库程序读取 27 份原始数据、共 **204,808,192 字节**，核对完整哈希及三份原输出控制，重新计算全部差异数量、最大误差、平均误差，并从保存的分片中间结果重新验证 BF16/FP32 求和和舍入关系。它也再次读取原 checkpoint 的 8 MiB 区间，与保存权重逐字节核对。复核实际退出 0，约 74.59 秒、峰值约 272.47 MiB。

差异数量和最大误差要求准确相等；平均误差只允许统计加法顺序导致的 `rtol=1e-12, atol=1e-15` 差异。独立复核没有重做矩阵乘法，不构成另一套 GEMM 实现的验证。

## 保留的工具失败

最初准备时，误用 2 MiB 元数据读取器校验解释器文件，在运行前失败；后继使用有大小限制的流式文件哈希。首轮实际执行随后在导入 Torch 前被安装清单校验拦住：四个本地命令入口的 shebang 及生成的 NumPy 字节码与 RECORD 不同。

后继固定四个入口的实际路径/字节/哈希，通过不存在的字节码缓存前缀与 `-B` 避免消费生成缓存，其余库源码与二进制继续要求原 RECORD 哈希。未修改已安装库、模型权重或数学公式。准备失败、首轮退出 1、两个现场文件和后继成功退出均已保留。这些问题属于本次取证工具的适配，不是 MiniCPM5 或芯片的故障证据。
