# MiniCPM5 完整数值与缓存审计接入；Nemotron r11 新进展

MiniCPM5 新增独立数值审计和串行执行入口：**20 项数值／保存文件检查、16 项退出／生命周期检查通过**。审计会重新计算全词表输出与官方参考的误差，再独立还原全部历史缓存。此处是审计工具验证，尚未启动新的 MiniCPM5 采集或读取真实张量，不能视为模型优化通过。

Nemotron r11 截至 **2026-11-10 07:42:20 UTC** 已独立核对 **31／52 个阶段**：准备、9 项状态读写、21 项切分诊断。全部八种投影候选通过 **48／48** 次设备输出比较；卷积候选在已完成的 128、256 token 两种形状通过 **12／12**。完整模型服务启动及后续验收仍待完成；没有新增提速倍数。

## MiniCPM5 审计现在核对什么

| 内容 | 完整覆盖范围 | 失败时的处理 |
| --- | --- | --- |
| 官方参考输出 | 8 条原提示 × 4 帧，共 32 帧；每帧 130,560 个 FP32 分数 | 缺帧、换序、提示／续写变化或哈希不符即拒绝 |
| 三条配置的模型输出 | 两个 rank 各 42 个完整输出文件，共 84 个 | 两个 rank 必须一致；副本只计一次，共 96 帧数值指标 |
| 原预测位置观测 | 每次四个 BF16 观测点，共 3,145,728 字节 | 完整字节、形状、物理行、当前位置和帧映射全部校验 |
| 第二层完整缓存 | 84 次调用的 K、V，共 168 份完整缓存 | 独立还原全部 726,663,168 字节，并核对本配置的历史连接 |
| 实际任务结束 | 外部工具退出、采集协调进程、两个 rank、服务退出和清理记录 | 无实际退出或未清空则不能进入真实数据审计 |

读取 FP32 保存文件前，先核对文件身份、归属、大小和完整哈希，再在内存中解析受限的 PyTorch ZIP／pickle 格式。只允许原 FP32 存储和完整形状，不调用 Torch、NumPy 或模型加载器。禁止截断文件、异常存储、非有限值、重复 ZIP 条目以及未批准的反序列化函数。

数值重算沿用冻结的原 Python float64 实现和独立误差容差。模型门槛仍是 cosine ≥ 0.995、KL ≤ 0.02、最大误差 ≤ 2；参考 top1 间隔超过 0.5 时还要求 top1 一致。独立计算与原 FP32 计算之间的微小容差不改变这些模型门槛或最终失败分类。

此次补上了旧复核器的一个覆盖缺口：旧代码只遍历已有的参考证据，若某帧的证据缺失，可能没有触发该帧的哈希比较。新代码强制两个 rank 都提供完整、顺序一致的 32 帧参考证据。该发现针对本项目旧审计脚本，不能据此声称上游模型或推理仓库存在同样缺陷。

## 实际执行的前提

新入口要求采集任务的独立存活观察与实际工具退出记录相互匹配，包括原进程、启动时间、命令、会话、运行规格和源码审查。13 份原输出记录必须齐全；两个 rank 必须真实以 0 退出，协调进程和外层结果不能自证退出。实际服务身份、完整清理和递归进程组清空也要再次确认。

进入真实数据审计前，新进程取得串行锁，重新核对全部 1,255 个前序服务及原来源和科学计划。每个读取边界检查串行所有权、原进程消失和采集进程组清空；服务与存储状态至少每秒刷新，并在开始／结束时完整检查。保留原审计的 CPU 6、2 GiB 地址空间、600／605 秒 CPU、900 秒计时和单文件 2 MiB 上限。

数值核对通过后才进行完整缓存字节审计。这里“通过”表示保存的结果与原记录及计算一致，允许确认原模型仍然失败；不要求把失败帧改成通过。两条审计都完整结束才会写完成记录。审计入口不启动模型，也不会据此启动下一项实验。

源码准备核对了 **2,355 个源码／文本文件，160,569,062 字节**，保留全部前代固定版本和原科学计划。还没有真实运行规格；需要先得到 Nemotron 的实际结束／释放证据，再执行完整 MiniCPM5 采集，最后据采集的真实退出记录生成具体审计规格和审查。

## 测试证据和边界

20 项数值检查包括完整合成轨迹：读取 84 个输出文件、32 帧参考、全部 96 帧指标，并拒绝缺失参考和掩盖失败的汇总。为了让合成输出独立于原模型数据，这组完整合成测试只替换了原元数据验证器；其余原 84 次调用元数据兼容检查使用真实 JSON。合成测试中的 31／30／29 通过帧数只是测试数据，不是模型结果。

16 项生命周期检查覆盖缺失或失败的实际工具退出、替换会话／进程、改动源码计划、缺失输出、缩减历史、错误服务调用、rank 父进程或组错误、自证退出、清理失败，以及未获串行所有权时拒绝读取。它们使用合成元数据和模拟的拒绝路径，没有执行真实操作系统完整审计。中间一次测试因合成服务记录缺少 Job 字段失败，补齐测试数据后通过；实际验证门槛没有修改。

原 MiniCPM5 CPU 对照仍为 **29／32 数值通过、top1 32／32**；两个 BF16 候选仍为 **28／32、top1 31／32**，保持不合格。真实压缩空间是否够用、观测是否不影响模型、完整保存数据审计，以及相同当前输入＋自身历史的注意力重放都仍待验证。历史缓存差异尚不能解释为已证明的缓存错误。

这说明单 batch、单 token 的控制不能覆盖较长序列或多请求形状。阶段成功表示诊断按其候选／负控制要求完成，不表示原路径数值合格。这里独立检查了元数据哈希、进程身份、真实服务退出和进程组清空；最终完整原始字节审计仍未执行。

这些是局部正确性结果，不是端到端性能。未合格的原路径不能成为提速分母。冷缓存至 4096、长解码、槽位复用、生成／RNG／停止／文本／质量、真实 HTTP 四并发和配对性能等全部验收条件继续保留，15 个模型家族的目标仍在进行。
