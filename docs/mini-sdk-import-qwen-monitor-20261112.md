MiniCPM5 的独立 SDK 导入诊断复现了原异常，并完整记录了子进程退出和资源释放。Qwen3.5-2B 第五轮在冷缓存阶段启动时被监控中止，尚未完成冷缓存计算。本轮没有新增合格模型或推理提速倍数；既有收益与限制汇总在[模型提速总表](model-speedups-20261112.md)。

## MiniCPM5：失败发生在模型计算之前

本轮只在原 SDK Python 环境运行一次导入诊断，保留原 2 GiB 地址空间、600/605 秒 CPU、900 秒 wall、CPU 6、nice 19 和 2 MiB 单文件限制。完整历史与 47,925 条源码绑定通过后，子进程执行 `import torch`，在 Torch 的导入入口再次出现：

```text
ImportError: libcusparseLt.so.0: failed to map segment from shared object
```

该异常来自 Torch 加载所依赖的动态库；当时尚未导入后续 SDK attention 工具，也未执行模型或读取历史张量。CUDA 库名出现在这个主机 Python 环境中，不表示 Trn1 正在运行 CUDA 推理。

| 子进程观察点 | VmSize（KiB） | VmPeak（KiB） | VmRSS（KiB） | 线程数 |
|---|---:|---:|---:|---:|
| 导入前 | 159,176 | 315,360 | 150,300 | 1 |
| 失败后 | 362,644 | 1,699,632 | 201,400 | 1 |

峰值虚拟地址空间约 1.62 GiB。失败后的 VmSize 会受加载器撤销映射影响；峰值也不记录失败映射所申请的大小。因此这些观察与原 2 GiB 上限尚不足以证明具体失败原因。异常未提供 errno，报告明确保留这一缺失，没有把它推断为 ENOMEM、物理内存耗尽、磁盘不足或芯片故障。

与上一轮不同，本次父进程完整记录了子进程真实退出码 1。外层工具也退出 1；主任务独立核对两个进程均已消失、两个进程组为空、两次当前重任务服务列表为空，并实际重新取得原串行锁。四份诊断文件完整保存。此前原生 24 份输出和 24 项展平恒等对照仍成立，但完整五阶段 PV 对照尚未通过，旧轮次缺失的 SDK 退出记录也没有补造。

## Qwen3.5-2B：保留完成阶段，修正监控窗口

第五轮实际完成了 42 项原生预检、96 个状态 buffer 的 192 次填充和 192 次清零比较，以及 numeric32 的 32/32 argmax 对齐。随后外层报 `Competing active heavy service` 并退出 1。冷缓存目录只有阶段配置与空日志，没有冷计算结果；长解码、质量和候选配对性能尚未进行。

本次没有保存冲突的活跃服务名单。源码中“先枚举已声明阶段、后获取活跃名单”的不同步窗口已在交错测试中复现，但不能据此断言它就是第五轮实际失败原因。清理核对包含 9 个记录过身份的进程和 21 个声明服务；原锁已释放。

新版监控保留前后实际名单，并重复核对阶段配置、进程身份和服务资源；仅允许合法阶段切换，未知服务、身份置换和两个同时运行的阶段仍须拒绝。主任务又发现合法的 `env` 到 Python 启动切换可能在两次进程读取间发生，交错测试复现了这一误拒绝。v6 对此增加一次完整重认证，并移除新引入、没有实测依据的 5 秒扫描门槛，保留最多四轮核对及原单命令和总运行期限。

主任务独立执行了全部 109 项适用检查：首次命令有一个测试模块名拼写错误，已执行的 97 项通过；修正模块名后剩余 12 项通过。旧源码保持冻结。原科学逻辑的 AST、leaf v2、数值门槛和运行资源不变；这只是源码与模拟验证，新版尚未实际运行。

另一个工具问题是：本机 systemd 对 SIGTERM 记录 `ExecMainCode=2 / ExecMainStatus=15 / Result=success`。它表示服务终止状态，不能当作模型执行成功；逻辑成功仍要求正常退出码 0。
