# Dory：原始 BF16 投影、单 token 差异与批量依赖

后续进展：完整原权重短轨迹已运行，投影后端因果对照和独立复核见[完整 CPU 前向记录](dory-full-original-cpu-20261108.md)。下文保留本轮局部投影的历史结论。

2026-11-08，已完成 Dory 原始 4B 权重的全部线性投影检查：覆盖 72 个物理层和输出头，共 181 组、289 个原始矩阵，在每次输入 1、7、32 个 token 的条件下运行 543 个案例。**975 项后端比较中 781 项逐字节一致、194 项不一致；全部差异发生在单 token 条件，最大绝对差为 0.000244140625。** 预先声明的精确一致性条件没有通过，未放宽标准。

这是一轮真实尺寸、原始权重的投影诊断。**尚未执行原始 4B 模型的完整前向、生成或 Neuron 基线，没有新增整模型合格结果或提速倍数。** 同一输入随批量改变也可能得到不同的 BF16 输出，后续整模型对照需要固定实际计算后端、批量和调用顺序。

固定模型为 `nvidia/NVIDIA-Nemotron-Labs-Dory1.0-4B-BF16`，修订 `f6c832e6963ddb74f62c75813a3e8c74b1af67b1`。原文件 SHA-256 为 `207483664dfef54c4c4438863260d3ba423bf3d6009b43fe84264b281e9fda23`，包含 507 个 BF16 张量、3,975,229,440 个参数。本轮原精度、权重内容和模型配置均未修改。

参考端使用已经构建和验证的官方 vLLM 提交 `75fc05a53a366068f534a61ab3ee6b50485419f2`、PyTorch 2.14.0+cpu。保持真实的 QKV、Column/RowParallelLinear、MergedColumnParallelLinear 和 ParallelLMHead，以及各自的权重加载和加载后处理。实际观察到 **543 次 oneDNN 调用**，每个案例一次，没有把静态配置当作实际后端证明。输出头调用实际线性计算接口，本轮不应用最终 logits 的学习缩放，也不执行采样。

181 组由 36 个注意力层的 QKV、门控、输出投影共 108 组，36 个 MLP 层的 gate/up、down 共 72 组，以及输出头 1 组构成。72 个多矩阵组合同时比较合并和分开的 `F.linear`；109 个单矩阵组比较官方结果与 `F.linear`。官方加载后的全部 181 组权重在后处理前与原始矩阵或其正确拼接逐字节一致，排除了本轮比较中的权重加载/拼接内容变化。

| 输入 token 数 M | 官方 oneDNN 对合并 F.linear | 官方 oneDNN 对分开 F.linear | 合并对分开 F.linear |
|---|---:|---:|---:|
| 1 | 51/181 一致 | 8/72 一致 | 72/72 一致 |
| 7 | 181/181 一致 | 72/72 一致 | 72/72 一致 |
| 32 | 181/181 一致 | 72/72 一致 | 72/72 一致 |

分母是投影组数，并非整模型生成请求数。单 token 下，官方对合并路径共有 130 组、273 个元素不同；官方对分开路径共有 64 组、162 个元素不同。两组比较包含重叠输出，不能把元素数相加当作独立错误数量。全部输入和输出均为有限值。

输入有明确边界：K=2560 使用既有 `history_default_truncation` 32-token 提示的原始 embedding 行，并在各组中复用；K=4096 和 K=7168 使用确定性的归一化合成向量，先按 FP32 归一化再转 BF16。所有矩阵的尺寸和权重是真实的，但这些输入不是完整模型逐层运行得到的中间激活。因此，本轮不能证明完整模型的数值质量，也不能把观察到的最大差当作任意输入的误差上界。

在保存输出后，进一步做了明确标记为事后分析的批量前缀比较。先核验较小输入确实与较大输入的前几行逐字节相同，再分别检查每个后端自己的输出，不重跑矩阵乘法。

| 后端 | M=1 对 M=7 的相同行 | M=1 对 M=32 的相同行 | M=7 对 M=32 的前七行 |
|---|---:|---:|---:|
| 官方 oneDNN | 42/181 一致 | 42/181 一致 | 181/181 一致 |
| 合并 F.linear | 64/181 一致 | 64/181 一致 | 181/181 一致 |
| 分开 F.linear | 10/72 一致 | 10/72 一致 | 72/72 一致 |

这 1,302 项额外比较说明，**在本次原权重、CPU 和输入条件下，两条后端路径都具有批量依赖**。不能因为 M=7/32 后端间一致，就推断逐 token 解码时也一致；也不能用不同批量的结果充当精确对照。它不直接证明某个上游实现存在正确性缺陷，更不能据此判断生成质量下降。此前小模型 BF16 的 28 次完整调用一致、FP32 精确门槛失败的记录都继续保留。

独立复核程序仅使用 Python 标准库，重新读取整个约 7.95 GB checkpoint、重新计算全部 507 个张量哈希、重新拼接计算 181 组原始投影哈希，并检查 **1,311 个完整原始输入/输出文件，共 252,108,800 字节**。975 项比较的精确性、不同元素数和最大绝对差全部重现；原始 embedding 输入也直接从 checkpoint 恢复。合成输入的字节和前缀关系已核验，但没有宣称其归一化计算被独立重算。事后批量分析又重新核验全部保存文件。两项检查均没有导入 Torch/NumPy，也没有重复执行模型或 GEMM。

实际运行退出码为 0，独立复核与批量分析退出码均为 0。数值采集耗时约 126.42 秒，峰值 RSS 约 9.46 GiB；这些数字包含权重加载、哈希、保存及诊断开销，**不是推理延迟或提速数据**。任务使用单个 CPU 核、单线程和串行锁，输出保存在 NVMe，保持根盘 28 GiB、NVMe 8 GiB 的空闲下限，没有扩容 EBS。

保留了一次本地工具失败：首轮已经加载原权重，但读取旧校验记录时将 `loader.tensors` 错写成顶层 `tensors`，在任何投影计算前触发 KeyError。v2 仅修正这一处记录读取；原失败、原代码和日志保留，数值计划、批量、权重、预算和比较标准不变。这是本地诊断工具问题，不是模型或官方 vLLM 故障。
