## Qwen3.5：PyTorch 虚拟模块被误当成实验源码

上一轮修复了运行器将自身监督服务误判为竞争任务的问题。第二轮确实越过该位置，启动了原生子进程；失败位置变成了预检完成计算后的已加载来源检查。

PyTorch 的 `torch.ops` 是动态命名空间，其类把 `__file__` 标记为相对字符串 `_ops.py`。自有校验器直接把所有模块的 `__file__` 相对当前目录解析，因此把它识别成了不存在于来源清单中的实验文件。`torch.classes` 存在相似的 `_classes.py` 标记。这是实验运行器的来源识别错误，现有证据不支持归因于模型数值、采样算法或 Neuron 芯片。

本轮实际工具会话 `3958` 退出码为 `1`，原生子进程退出码也为 `1`。完整模型阶段没有启动，没有生成性能结果。后继精确认证虚拟对象与其真实定义模块，包括原 Python 3.10 环境下的源码摘要、单例身份和构造／查找函数；普通实验源码继续核对完整摘要，并避免动态属性查找产生副作用。44 项纯检查全部通过，包含原 38 项检查与 6 项新回归测试；新回归还检查身份替换、来源篡改、缺少摘要、未知相对文件及动态属性查找。真实原生重跑仍待完成。

原 BF16 权重、FP32 循环状态、TP2/B4/context4096、12 个图、203 份原始向量、冷缓存、1,541 步长解码、槽位复用、quality96 和匹配 HTTP 对照继续保留。

第三轮工具会话 `91265` 实际退出 `1`，发生在创建准入和计算输出之前。主任务更新了顶层来源字典，却复用了第二轮的历史扩展清单，导致最近 MiniCPM5 实验的 18 项来源没有进入历史校验视图。严格校验正确拒绝了这份配置。该进程的 PID 没有在退出前捕获，记录明确保留这一缺失；实际工具退出、两遍 21 个声明服务检查、进程扫描及原锁空闲观察已经保存，没有补造进程身份。

第四轮从已认证的原恢复记录重建 44,532 项继承来源，加上 3,379 项不重叠的新增来源，使历史视图与顶层 47,911 项字典完全一致。原检查器验证全部 110 条历史，并确认旧漏项配置仍会被拒绝。运行源码、科学检查与资源限制均未改动。工具会话 `33012` 已启动并独立记录实际进程和持有的原锁；启动本身不表示模型验收通过。

## MiniCPM5：先排除配置问题，再做固定输入实验

首次启动的配置把三个已继承的比较工具和一个审计工具再次放入新增来源集合。原校验器明确要求新增来源与继承来源不重叠，因此拒绝了配置。实际工具会话 `77141` 退出 `1`，尚未创建输出目录或启动任何原生计算子进程。这次错误来自主任务准备的配置。

修正配置时，主任务从原模型、原生审计、保存算子比较及独立审计的记录重建完整来源字典，并核对四个原摘要；第二轮保留 47,839 个继承来源，添加 55 个后续来源。它完成前面的原始比较重建后，在重建独立审计的旧运行范围时遇到另一个接入错误：调用原范围组装器时漏传已认证的运行配置，导致 `KeyError: contract`。工具会话 `35844` 实际退出 `1`，尚未创建输出目录或启动计算子进程。

后继只补传已经由原重建流程认证的配置，仍调用原范围组装器。18 项原检查和 4 项针对性回归全部通过：旧调用确实失败，新调用保留所有进程、服务及原范围字段，缺少认证配置仍拒绝。第三次命令还因主任务误传占位摘要而在读取配置前被拒绝，这条命令错误另行保留，不算科学实验结果。第四轮工具会话 `83513` 使用实际摘要启动，保留全部 107 条串行历史、47,839 个继承来源与 61 个新增来源，共 47,900 项。原科学源码和资源限制没有改变。

第四轮实际结果已核对：原生阶段完成，24 份输出与原结果逐字节一致，24 项展平恒等检查也全部一致。SDK 阶段在导入原 PyTorch 时报告 `libcusparseLt.so.0: failed to map segment from shared object`。当时原 2 GiB 地址空间限制仍生效，但目前不能据此断定限制就是根因，也不能把库名解释为实际执行了 CUDA。随后父进程在收尾时触发 `Exact child identity while live`，导致缺少 SDK 子进程的持久化退出记录；没有推测或填补该退出码。外层工具实际退出 `1`，三个已记录进程均已退出，原锁空闲。

独立复核会话 `93216` 随后实际退出 `0`：从原六份报告重建全部 1,284 项描述，重读 24 份新输出（98,304 字节）、48 份原目标及展平文件（196,608 字节）、所有对应事件和统计，精确复现整个原生阶段审计。54 个文件的结果目录保持一致。该复核仅确认原生阶段；没有 SDK 变体结果，没有完整 60 项原输出控制，也没有完整实验成功结论。

科学问题仍然是：先前 48 组数据的 BF16 注意力概率全部相同，其中 47 组有效 V 也相同，但输出 context 均不同。新实验使用保存的固定输入，先验证原生 24 份和 SDK 36 份原输出能逐字节重现，再比较拆分／合并计算、形状布局和中间舍入，并计算 96 份整数参考。完整方案包含五个独立计算子进程、4,392 份派生原始文件与 1,752 条事件，计算后再做原输出控制。

该实验用于判断差异原因，不直接建立模型正确性或性能结论。原 4096 冷缓存、长解码、请求槽位复用／隔离、quality96 和匹配 HTTP 测试仍须独立完成。

## Dory 与 LFM3 的验证边界

Dory 的历史环境开关有部分没有记录。后续设计明确使用新受控诊断环境，不能称为历史环境重放。库文件已存在、被搜索或被映射，都不足以证明某条依赖最终选择了它；符号绑定还可能受其他库影响。剩余工作已缩小到候选库与启动路径的内容覆盖，以及能区分实际请求者和成功返回库的加载器证据。原两轮计算、共 56 份独立注意力历史和 TP1 保留。

候选 ELF 内容工具通过 21 项独立纯检查，方案只读取三份新二进制文件作为数据，其余 24 份使用已有元数据。保存数据预览得到 105 条依赖边，39 项仍缺观察；所有实际选中库字段保持为空。该工具尚未执行，候选内容关系也不能替代真实加载器选择证明。

LFM3 的完整 CPU 接入保持原用例、输入生成方法、批次和逐字节检查。纯测试通过尚不能证明实际模拟器与原执行限制兼容。静态检查确认，`nki.simulate` 的框架转换层在接收 NumPy 参数时也会尝试导入 PyTorch；目前未找到普通导入必然触发禁止操作的完整路径，实际兼容性与总预算仍待实测。此前模拟器 BF16 输入写回会改变 NaN 位模式的失败记录保留，诊断用的精确写回适配器仍不用于设备、模型或性能路径。

后续来源审阅保留原 570 项并扩展到 590 项，随后发现完整 CPU v1 的启动环境遗漏 `PYTHONPYCACHEPREFIX`。原 NumPy 字节码例外要求环境变量、解释器缓存前缀及原校验器配置完全一致，13 项纯检查复现了遗漏会在读取 payload 前拒绝。因此，前面的源码审阅不能视为运行许可，完整 CPU v1 保持不运行。最小后继将显式设置不存在且非符号链接的隔离路径，继续禁写字节码；无需放宽文件或资源预算，也不需要因此切换解释器。实际模拟器兼容性仍待验证。
