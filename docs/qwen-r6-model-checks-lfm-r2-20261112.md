# Qwen 配对模型检查、LFM 重跑与诊断工具修正

2026-11-12 接续原 15 个模型家族。Qwen3.5-2B r6 的两侧模型检查和向量对照均完成，但后续 API 启动失败，整轮实际退出 1。LFM3 完整 CPU r2 已通过前置核对并启动实际 worker，正在原串行锁内执行完整对照。本轮没有新增合格模型或提速倍数；[各模型提速总表](model-speedups-20261112.md)保留已测数字、基线与适用范围。

## Qwen3.5-2B：模型检查通过，HTTP 阶段尚未完成

这轮比较标准 CPU sampler 与候选 sampler，模型、官方权重、精度和原验证要求保持。原生预检完成 42 项序列化案例、13 项拒绝对照、4 项 worker pickle，以及 expanded stride-0 反例检查。随后 baseline 与 candidate 均完成以下步骤：

| 检查 | baseline | candidate |
|---|---|---|
| 状态复制 | 完成 | 完成 |
| 原 32 项数值检查 | 通过 | 通过 |
| 原 84 项冷缓存检查 | 通过 | 通过 |

| 203 个原始向量对照合格历史基线 | 全部逐位相同 | 全部逐位相同 |

含共享预检在内的 11 个阶段，真实子进程和服务均退出 0。原始向量比较由经过认证的原生子进程执行；主任务随后独立复核保存的完整 JSON、阶段退出与原验证器，未把读取 JSON 表述成重新读取原始张量。

之后 baseline capture API 在启动时失败，尚未进行实际采样采集、quality96 或匹配 HTTP 测速。API 子进程实际为 -9，监督进程和协调进程退出 1，外层工具也实际退出 1。主任务核对全部 26 个已记录进程均已退出，并对全部 21 个声明服务执行两遍完整、相同的物理排空检查；原锁当时可取得并已释放。

失败现场的 API 日志为 15,008 字节，traceback 停在 `async_llm.py:207`。自有监督代码 v6 在读到第一段 `Traceback (most recent call last)` 后立即抛错，进入 finally 并终止仍存活的 API，未继续读取管道尾部。这能解释缺失后续异常日志，但 **API 启动的底层根异常仍未知**，没有证据把它归因为 OOM 或某个模型算子。

后继 v8 将首次错误保存为不可撤销的失败状态，在原 45 秒清理窗口与阶段剩余期限内继续收集输出，必要时 TERM/KILL。错误后即使子进程退出 0，整阶段仍失败；EOF 只表示管道结束，不宣称 traceback 必然完整。协调进程等待同一绝对期限，并以 finally 保证等待失败时仍进入原清理。客户端操作前后均检查失败状态；已经提交的 HTTP 操作不能保证瞬时取消，但其结果不被接受，也不会开始下一操作。

主任务独立复跑 128 项检查通过，包括原 109 项与新增 19 项日志／失败路径模拟。测试拒绝 ctypes、Torch、NumPy 等原生相关导入，没有启动真实 API。科学 driver、native leaf、模型精度和资源限制未变。v8 尚未生成当前可运行配置，也没有修复或重新实证 API 的未知根异常。

## LFM3：完整 CPU r2 已启动实际 worker

上一轮 r1 的原环境 291 批／3,716 个案例完成；新环境只有 231 批／2,967 个案例具有零退出记录。第 232 份报告虽已保存，子进程和 worker 均退出 120，外层退出 1。日志达到 256 KiB 上限，末尾为重复语法警告；底层 flush 失败仍是解释，现场未保存直接的 EFBIG 异常。旧输出与失败记录保留。

r2 使用已审核的日志处理 v3：只对四条完整匹配的已知警告去重，并保存出现次数；未知警告和错误继续转发。原 592 份执行源码摘要全部保留，新增三份，共 595 份。三遍各 3,716 个案例、每遍 291 批，再加一个对照子进程，共 874 个子进程，原资源限制不变。若警告收据自身失败，可能无法保存结构化失败 JSON；真实非零退出仍使任务失败。

主任务独立比较 r1/r2 配置并通过真实 `read_bundle` 校验后，启动了 r2 外层进程。随后外层完成历史排空、当前源码、磁盘余量与服务检查，确认实际 worker 启动。主任务再独立核对 outer／worker 的 PID/start、服务 invocation、原锁描述符、准入文件和最新交接记录，服务处于 active，已进入 original fixture 阶段；全量结果和终态仍待完成。其已绑定的交接记录保持不变，实时观察单独保存。

## MiniCPM5：修复追踪器的超时交接窗口

此前 SDK 导入失败仍为 `libcusparseLt.so.0: failed to map segment from shared object`，对应系统调用 errno 尚未取得。本轮推进的是收集该错误所需的原生追踪接口。

源码审阅发现，自有 backend 先取得 Popen 的 wait lock，再返回给 adapter；若原 900 秒 alarm 正好在返回或赋值之间到达，清理代码可能找不到已取得锁的对象。释放锁与更新状态之间也有相同窗口。后继 backend v2／adapter v3 改为先保存对象引用，再显式交接；仅在非阻塞锁操作与状态更新的短窗口内暂存 alarm，恢复原 handler 后立即交付，原 timer 持续计时。无法判断交接状态时保留句柄和串行锁，避免猜测已经清理。

主任务独立复跑 backend 37 项、adapter 26 项模拟检查通过，包含返回指令前、赋值指令前、acquire/release 内部及 handler 恢复处的中断。测试禁止原生相关导入，进程、信号和锁均使用模拟对象。

早期 v1 测试误经历史模块导入 ctypes，违反当时只读源码测试范围。该偏差及真实退出记录完整保留，不能把那次 21 项 mock 通过算作符合范围的源码检查。后继采用延迟 factory 与选定原类 AST 的测试方式；真正 caller 的历史导入入口仍须修正。当前解释器、ctypes/libc 的原生来源与实际提供方认证、完整 outer 接线及真实追踪均待完成，没有新增模型数值或性能结论。

## Spark-X2.6-4B：官方权重清单与原生诊断源码

固定官方版本 `aa074aa851209a683aeaf5f99a8e25a642d94541` 的两份小型 JSON 已取得并独立核对。五个原始 safetensors 分片共 8,224,192,408 字节；290 个索引键等于原 291 个状态键去掉共享 embedding 的 `lm_head.weight`。尚未下载权重，不能把元数据核对算成权重加载成功；剩余磁盘还须容纳保留空间、下载 staging 和后续编译。

原生诊断 core v2 已完成源码审阅，13 项标准库检查独立复跑通过。计划使用原权重，执行 36 层 × 3 种输入形状 × 2 rank，共 216 项 QKV 投影诊断；并将实际缓存函数与官方 DynamicCache 对照，覆盖两种缓存、两 rank、每组 534 步，共 2,136 步。缓存与权重分片要求字节相同；QKV 舍入差异仅记录为诊断，不能替代或放宽原 logits 门槛。

进一步核对发现，trace 中虽有乱序请求元数据，core 却按槽位排序构造物理 B4 输入。因此该计划当前只检查排序后的缓存语义，尚未覆盖真实 host 请求重排／输出还原或任意物理行排列。固定 SDK 源码确实包含排序、补齐和还原路径；64 组符号映射一致也不等于执行 SDK。后继需保留原 534 步并补上实际 host 与排列对照。

目前没有执行 Torch 张量、TP2 collective、Neuron 编译或缓存别名验证。fresh allocated CPU 缓存也不等于新进程整模型冷启动。服务入口保持关闭，完整数值、冷缓存、长解码、槽位复用、quality96 和 HTTP 仍待完成。
