候选八组的抽样地址检查均通过。单行输入 `[1,1,11328]` 两种写法均通过，说明只用单 token、单请求测试不足以发现本次问题。

源码里的改动是将长度列表换成明确的累计边界。两种表达的预期数学含义相同，输出形状也相同：

```python
# 原写法，指定三段长度
parts = projected.split([5120, 6144, 64], dim=-1)
# 候选写法，指定两处分界位置；5120 + 6144 = 11264
parts = torch.tensor_split(projected, (5120, 11264), dim=-1)
```

一个具体例子：输入 `[1,128,11328]` 的第一段输出在坐标 `[0,1,0]`，应该读取输入的平坦元素索引 `11328`。原写法生成的 HLO 计算图却映射到 `5120`，仍落在第一行中。第二行另外两个被抽样的通道同样映射错误。这把问题缩小到当前编译路径的拆分及后续布局映射；只比较形状、编译是否成功或 CPU 结果都不足以验收。

这轮 Trn1 使用 Python 3.10、PyTorch 2.8.0、torch-xla 2.8.1、torch-neuronx 2.8.0.2.12.22436+0f1dac25、neuronx-cc 2.23.6484.0+3b612583，且 `XLA_DISABLE_FUNCTIONALIZATION=1`。编译参数和源码指纹保存在下方证据中。该结果不能外推为其他版本、所有形状或所有 split 都有问题；本轮没有进行 CUDA 对照，也没有证据把它归因于 Trn1 硬件缺陷。

这里的优化首先是正确性修复。还没有合格的整模型配对性能分母，不能把原路径输出错误换算为加速倍数。原写法是预期失败的对照，阶段报告外层 `passed=true` 表示对照成功执行并记录；内层 `primitive_passed=false` 和 `device_exact=false` 才是其数值结果。
