# MiniCPM5：真实双分片收集与完整 BF16 投影

2026-11-08，已完成真实双进程验证。两个进程使用 Gloo 通信，按原 rank/head 顺序收集完整 context，然后各自用原 BF16 权重执行一次完整输出投影。**原生 1,231 token 和 CPU 补齐后的 2,048 个位置，两种完整输入在两个 rank 上均准确复现已保存结果。**

本次排除了“单进程拼接可行、真实通信未验证”这一缺口。尚未运行第 0 层整模型候选，也没有新的质量通过或提速倍数。现有各模型提速表保持不变。

## 实际执行的对照

固定 `torch 2.8.0+cu128`，计算全部在 CPU；显式建立 Gloo 子组，成员及顺序为 `[0,1]`。每个进程读取自己的原始 1,024 维 context，以及原 checkpoint 中的完整 `[2048,2048]` BF16 矩阵。原生长度使用 2 个线程，CPU 补齐长度使用 1 个线程，与上一轮固定输入实验一致。

| 输入 | 每个 rank 的完整输入 | 原分片乘法与实际 BF16 求和 | 实际收集后的完整输入 | 完整 BF16 投影输出 |
|---|---|---|---|---|
| 原生 context | `[1,1231,1024]` | 两个 rank 均精确复现 | 两个 rank 均精确复现 | 两个 rank 均精确复现 |
| CPU context | `[1,2048,1024]` | 两个 rank 均精确复现 | 两个 rank 均精确复现 | 两个 rank 均精确复现 |

“精确”要求完整张量的字节、形状、步幅和偏移一致，不只比较最后一个预测位置。运行先检查本 rank 的 BF16 分片乘法结果，再实际执行 BF16 `all_reduce`，与原分片求和输出核对。候选路径则执行 BF16 `all_gather`，按最后一个维度拼接，再调用一次完整 `F.linear`；候选输出没有再次求和，也没有转换到 FP32。

原矩阵从官方 checkpoint 的 8 MiB 区间读取，其 SHA256 为 `f641e83dd6533cd4c9ea6f5b3689d4c952c86ca18c7e765db0399adfd259ed78`，两个原列分片也校验通过。两种情况下输入和权重在执行后保持原值。

执行处于推理模式。通信接收缓冲区用普通张量分配，允许通信完成时写入；这不改变 BF16 精度、输入或权重。此次没有发生运行失败。

## 与此前误差结果的关系

[上一轮完整 context 对照](minicpm5-fixed-oproj-20261108.md)已发现：保持 CPU context，仅切换为完整 BF16 投影，与原生输出不同的元素从 802,431 / 2,521,088 降至 2,967 / 2,521,088。仅加宽分片求和不能改变结果。

本次实际双进程输出与那一轮的完整 BF16 输出完全一致。因此局部候选已在真实通信中复现，但没有增加新的最终 logits、KL、生成质量或吞吐证据。局部误差缩小是否有益，仍取决于完整轨迹。

## 保存数据与独立复核

两个进程各保存两种长度的完整收集输入、完整投影输出和分片求和控制，共 12 份新原始数据、80,584,704 字节。运行含元数据约占 80,637,952 字节，存放在 NVMe；没有扩容 EBS 或删除已有结果。

运行会话 `15156` 实际退出 0；两个工作进程也均实际退出 0。控制程序约 20.94 秒，单个工作进程峰值约 639 MiB。这包括依赖验证、数据读写和进程启动，**不是推理性能基准**。

退出后，独立标准库程序读取 20 份新旧原始文件、共 129,265,664 字节，重新拼接原 CPU context、切分原生 context、逐字节比较全部 12 份新输出，并再次读取官方 8 MiB 权重区间。复核会话 `93505` 实际退出 0，约 1.18 秒。复核程序没有导入 Torch/NumPy，也没有另行重算矩阵乘法；它验证保存结果与既有对照的一致性，不声称另一套 GEMM 实现的独立验证。
