# MiniCPM5 第二层解码重放：原输入、内存排列与缓存视图

MiniCPM5 第二层注意力重放的输入准备已覆盖全部 **36 次原解码调用**，并通过 **15 项元数据与位模式检查**。三条配置、两个 rank、每配置六次解码均保留，每次包含全部四个请求槽位。此轮没有读取真实张量、运行新的模型或得到新的提速倍数。

这一步解决的是重放可信度：将原始数值放进新的张量后，仍须恢复原形状、内存排列、掩码、位置和缓存读取方式。否则，即使数值相同，也可能换了一条计算路径，无法把差异归因于历史缓存。

## 已经对齐的原始输入

程序重新读取并认证原调用 JSON，依据原提示长度、续写 token、解码步数和槽位，重建四路实际输入。全部 36 次调用都与原记录的完整哈希精确一致：

| 项目 | 保留的条件 |
| --- | --- |
| 当前 token、位置、槽位 | 原 int64 CPU 执行表示，原物理槽位顺序 0、1、2、3 |
| 历史注意力掩码 | 仅允许当前位置之前的历史；当前位置由独立当前 K/V 分支处理 |
| SDK 实际入口掩码 | 原 bool 类型、形状、排列和全部字节哈希 |
| 归一化当前输入 | 每次完整的 `[4,1,2048]` BF16 数值，以及原内存排列 |
| 历史 K/V | 每 rank 保留全部四个槽位、4224 个位置，包括填充区 |
| 预期注意力输出 | 每次完整四行输出，共 144 行；两 rank 是副本，去重后为 72 行 |

原逻辑提示顺序是槽位 3、1、0、2，实际张量行顺序是 0、1、2、3。重放明确恢复这层对应关系，并根据原 fixture 检查 token 与位置，不能直接把提示列表当成物理行。

预填充只保存了预测位置观测，不能当作完整预填充输入。本次 36 次重放准备针对原轨迹中的全部解码调用；完整 84 次原轨迹采集与官方 32 帧数值审计仍是前提，原整模型验收范围没有缩减。

## 连续保存的数值不等于原内存排列

原 `PredictionHooks` 将观测值保存为连续字节，同时单独记录原张量的形状、步长和偏移。全部 36 次解码中，第二层归一化输出的形状都是 `[4,1,2048]`，原步长是 `[1,4,4]`；保存后的连续数值排列则对应 `[2048,2048,1]`。

新增恢复函数只重排 BF16 的 16 位原始字，不进行浮点转换，恢复原 `[1,4,4]` 排列。测试覆盖全部 **65,536 种 16 位模式**，包括特殊浮点编码和负零，逐字验证没有信息丢失。直接把连续保存数据作为原存储的负控制会得到错误排列，已被测试识别。

这不是已经确认的模型错误：采集本来就同时保存了连续数值和原布局信息。这里是在后续重放中正确使用这些信息，避免新的实验误差。

## 缓存需要保留完整存储，再让原 SDK 读取

原每份 K/V 缓存是 `[4,1,4224,128]`，每份 4,325,376 字节。SDK 按当前 128 或 2048 token 桶读取前部视图；视图仍保留完整缓存的物理 batch 步长 540,672。

因此，重放先恢复完整缓存，再调用原 `KVCacheManager.get_kv_by_layer_id`。不能把有效前缀剪出后另建连续张量来替代原缓存视图。两个 rank 的当前输入和注意力输出虽然是副本，它们的缓存属于各自的 K/V 头，仍分别保留和校验。

## 位置编码和权重准备

核对了 13 个固定版本的 SDK／观测函数。原模型第 0 层生成 RoPE 的 cos/sin，随后传给第 1 层；重放需要保留这条非空缓存调用路径。原 `RotaryEmbedding` 对传入张量只使用设备与类型，数值由原位置、维度与频率基数决定；使用相同原 SDK 实现、BF16 CPU 类型和原位置可以准备相同路径。源码推导仍须由实际输出重放验证。

原官方 safetensors 头信息已明确第二层 Q、K、V、O 四个完整 BF16 矩阵及两个 rank 的八个分片范围。Q/K/V 按输出维切分，O 按输入维切分。真正运行时仍要从已认证的官方权重读取对应原字节，与实际模型参数逐项比较，不能只凭形状或头信息宣布权重一致。

准备时发现完成配置中没有 `moe_mask_padded_tokens` 字段；原 SDK 明确以 False 为默认值。准备脚本按该原实现读取缺省值，没有改写模型配置。首次准备失败记录保留，修正后源码准备退出 0。

## 当前可以和不可以得出的结论

15 项检查通过，验证了全部原解码元数据、物理行映射、原掩码、完整缓存布局、官方分片范围及 BF16 位模式恢复。检查没有导入 Torch、NumPy 或原生模型运行时。

原生注意力调用初稿也已保存。它计划使用原模型、原 SDK 缓存视图和恢复布局后的完整输入，调用第二层注意力，并要求完整四行输出逐字复现；尚未完成实际运行审查、官方原字节分片校验接入、真实数据加载和原生执行验证，不能直接视为可运行或通过验证的优化。

后续顺序仍是：完成原 84 次采集及无干扰检查 → 独立复核全部缓存、完整 logits 和官方参考 → 在串行任务中重放全部 36 次自身历史解码 → 只有完整输出精确复现，才能开展相同当前输入下的配对历史比较。

原 CPU 对照保持 29／32 数值通过、top1 32／32；两个 BF16 候选保持 28／32、top1 31／32。失败结论不变，缓存因果尚未证明。冷缓存至 4096、长解码、请求槽位复用、生成／RNG／停止／文本／质量、真实 HTTP 四并发和配对性能仍是整模型条件。
