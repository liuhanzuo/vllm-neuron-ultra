## 适配时必须保留的语义

注意力的隐藏宽度为 2560，Q 与门控投影宽度为 4096，K/V 投影宽度为 1024，单个 head 维度为 256。不能由“隐藏宽度 ÷ query head 数”推导 head 维度。Q/K 归一化位于 RoPE 之后，且 query、注意力输出门控、MLP 和词表 logits 均含各自的学习缩放参数。

模型有 72 个物理子层，原配置使用两次循环，单次完整前向访问 112 个子层。重复循环共享物理权重，但 `per_loop` 缓存保留 **56 份独立注意力历史**，其中 42 份为滑动窗口、14 份为全局注意力。减少循环次数或改成 `last_loop` 会改变计算或缓存语义，不能作为同一基线下的优化。

生成配置中的停止 ID 是 **2（`</s>`）和 11（`<|im_end|>`）**；tokenizer 的 EOS 和 padding 都指向 11，BOS 为 1，并默认不自动追加 BOS/EOS。未来服务必须明确处理两个停止 ID。聊天模板默认开启 thinking，`medium_effort` 默认关闭，并默认截去历史轮次的 thinking；这些设置需要固定后再比较输出和性能。该 tokenizer 还设置了 `ignore_merges=true`，应使用兼容的原始后端，不能自行替换成简化 BPE。

## RoPE 的后端区别已经定位到源码

上游 Dory 的 CPU 测试使用 `CompilationConfig(mode=0, custom_ops=["none"])`，因此参考路径应核实为 `forward_native`。这个测试使用的小尺寸 FP32 场景并不能证明原始 BF16 大模型合格。

固定版本中的原生 PyTorch RoPE 在默认设置下按输入 dtype 做乘法和加减；CPU 融合实现先将向量转换为 FP32，完成乘加后再写回。两者公式相同，但舍入步骤不同。这个源码差异不是已证明的上游 bug；它意味着后续必须记录实际 dispatch、dtype 和编译设置，不能把两个后端当成同一个参考。

新取得的默认 RoPE 工厂、缓存、静态运算、dispatch 和 CPU 内核源码都已与固定 Git commit 的 blob 校验。已有本地参考只计算所需位置的三角缓存，上游实现先构建缓存再索引；已在位置 0、1、1023、1024、2048、262143，以及两种官方 theta 上完成 FP32/BF16 局部算术对照，结果见后文。官方模块导入与实际后端调度仍需另行验证。

## 可以推进的优化

首先建立原权重参考和 vLLM-Neuron 基线，再逐项测量以下候选。

| 方向 | 预期作用 | 必须验证 |
|---|---|---|
| 滑动窗口环形 K/V 缓存 | 对 42 份滑动历史只保留必要窗口，减少内存与读取 | 多次跨越 1024 窗口边界、绝对位置、两次循环隔离、长解码、槽位复用与恢复 |
| 共享循环权重与预编译子图 | 避免为重复循环复制物理参数和重复构造图 | 原始两次循环、输入重新注入、归一化顺序、缓存写回顺序 |
| QKV、gate/up 的合并计算 | 减少启动和访存开销 | 与原 BF16 投影逐层比较；合并计算可能改变舍入，不能只看耗时 |
| 归一化和学习缩放的融合 | 减少中间张量与访存 | FP32 累加、epsilon、缩放位置和最终 dtype 不变，完整质量门槛通过 |

当前透明 CPU 参考为方便核验保留全部历史，其 K/V 逻辑存储为每 token 229,376 字节。以下仅为理论张量容量，不含权重、激活、临时复制和框架开销：

| token 数 | 全历史参考 K/V | 42 份滑动历史各保留最多 1024 token 的候选 K/V |
|---|---:|---:|
| 1024 | 224 MiB | 224 MiB |
| 2048 | 448 MiB | 280 MiB |
| 4096 | 896 MiB | 392 MiB |
| 262144 | 56 GiB | 14 GiB + 168 MiB |

上述容量不代表实际峰值内存，也不证明声明的最大上下文能在本机或 TP1 Neuron 核上容纳。长 prefill 的工作区和循环中的中间状态仍需实测。

后续 Dory 实机工作仍排在正在运行的 Nemotron r7 和已准备的 MiniCPM5 注意力诊断之后。Dory 的 RoPE 局部算术已完成；仍需验证官方模块调度、真实权重加载、分词器与模板、投影/SDPA、原权重全模型参考和 Neuron 移植，以及原定冷缓存、长解码、槽位复用、质量与配对服务性能检查。

## 原始 BF16 权重加载代码已准备

加载程序现已实现并通过 **24 项源码与合成文件检查**。它按已核验的官方文件头依次读取 507 个物理张量，每个张量只分配一份底层字节缓冲，读取块大小限制为 1 MiB；按文件顺序同时累计整个 checkpoint 的 SHA256，只有完全匹配官方 LFS 校验值才返回权重。张量名称、完整形状、偏移和文件身份必须匹配，两个循环继续共用原来的物理参数。

实现计划通过 `torch.frombuffer` 让 CPU BF16 张量持有底层缓冲，避免先缓存整个文件再复制一份全部权重。有限值检查也按小块执行。当前只用小型合成文件与标准库 `memoryview` 验证了读取、哈希、缓冲寿命和中断处理；真实 PyTorch 缓冲所有权、官方权重值、实际内存峰值和原生模型构造尚未运行。这里的 7,950,458,880 字节只是权重数据量，不是实际峰值内存。

首轮反例测试中，替换文件已被“原文件失去链接”的检查正确拒绝，但测试错误地要求看到稍后的身份不匹配消息；已调整测试断言，生产代码未因此放宽。原失败记录保留。

该模块没有下载器、模型启动入口或自动执行路径。未来必须由串行运行器提供实际运行资格和资源检查，再调用加载函数。后续仍依次需要官方完整文件、实际加载验证、原生数值对照、Neuron 基线以及全部完整模型验收，不能把加载器测试算作模型完成或提速。

## RoPE 局部实测与完整保存数据复核已完成

两个官方 theta（10,000、10,000,000）、FP32/BF16、两组确定性输入、Q/K 和六个位置构成 96 种条件。不采集与采集各运行一轮，共 **192 次比较**，有限值、数值和字节比较全部通过。原生执行使用 CPU PyTorch 2.9.1，单线程、CPU 6，保留官方完整 262,144 位置缓存的计算路径。共保存 53 个完整张量、2,230,320 字节。

原生会话 20457 与运行后独立复核会话 56360 均实际退出 0。独立复核重新读取完整保存数据，以保存的旋转系数重放 FP32/BF16 乘加，原路径和候选输出均复现；它没有重新计算三角函数、执行官方整模型调度或加载权重。因此只证明这组位置编码局部算术，不提供整模型正确性、Neuron 基线或推理提速结论。

早期结果组装重复传入 dtype 的错误已在运行前修正，旧源码与失败记录继续保留。[实际结果、退出与复核证据](dory-r1-nemotron-r6-terminal-20261108.md)记录了测试范围和限制。
