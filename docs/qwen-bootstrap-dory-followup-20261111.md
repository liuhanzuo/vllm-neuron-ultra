## Qwen3.5：本地启动检查先于模型失败

原轮次保留真实失败：外层工具会话 `46709`，退出码 `1`。监督进程在读取运行记录时抛出 `Competing active heavy service`，没有写出自己的就绪记录，也没有启动原生子进程。协调进程随后报缺少监督进程记录，外层报缺少完整结果。

源码显示：首次监督进程启动时，自己的服务对象尚无保存的 owner 记录，因此 `started=False`；`live()` 已核对真实进程并填入 owner，却没有改变这个标志。后续排他检查仅凭 `started` 决定是否排除当前服务，因而会把已核对的自身服务判为竞争任务。这属于自有运行器的状态管理问题，不是 Qwen、vLLM 或 Neuron 数值错误的证据。

后继只调整排他检查对已认证当前 owner 的识别，保留原进程身份复核。38 项测试全部通过，其中 5 项新增回归覆盖：同一场景复现旧版失败、新版在没有监督进程就绪记录时通过、拒绝未知竞争服务，以及 PID、启动时间、参数、进程组或服务调用身份变化。原 33 项检查继续通过。第二轮外层工具会话为 `3958`，正在核对完整历史与原图缓存，尚无新模型结果。原失败源码和记录保留。原 BF16 权重、FP32 循环状态、TP2/B4/context4096、12 个图、203 份原始向量、冷缓存、1,541 步长解码、槽位复用、quality96 和完整 HTTP 对照全部保留。

## Dory：源码入口与实际加载结果分别验证

补充采集完整处理原有 70,764 条保存事件后，只读取其中明确认证的 Python 源码，没有导入目标库或扫描扩展范围。主任务复核了全部 102 份保存源码的字节数和摘要，并精确重建 28 处语法／文本引用。整个任务实际退出 0，进程消失，原串行锁已释放。

新材料已定位 `fs_io_C` 和 `spinloop` 的相关 Python 入口。`spinloop` 默认关闭，但 `GroupCoordinator` 在判断并行度之前会导入 `shm_broadcast`；**TP1 本身不能证明该导入路径没有发生**。Torch 的静态开关也只能说明条件路径，不能代替原运行环境中的真实库选择。

因此，原 13 条 vLLM 加载关系及 2 条 libgomp 选择关系仍保留为待验项。有限源码范围内没有找到引用，也不能推导整个包不存在引用。后续验证继续保留 Dory 原两轮计算、共 56 份独立注意力历史和 TP1。

## LFM3：把已定位的写回问题接入完整测试

此前[32 项完整对照及全部 BF16 编码检查](lfm-writeback-characterization-20261111.md)已支持模拟器输入写回路径会改变 NaN 位模式的解释。新适配器只在两个已认证的 BF16 输入提取位置使用精确写回，每例保留三次输入提取及一次输出提取的记录，结束或失败时恢复原函数。它仅供模拟器诊断使用。

完整测试前，新工具必须在原 NumPy 1.26.4 / ml_dtypes 0.5.4 与新 NumPy 2.5.4 / ml_dtypes 0.6.0 环境生成相同的原始测试数据，对 cache、updates、slots、期望输出分别比较全部字节的摘要。相同随机 seed 不足以证明输入相同。实际原实现／候选／恢复原实现三组控制通过后，才能执行原 3,716 例、291 批测试。

本轮 20 项检查验证的是上述接入逻辑、原完整用例与批次、失败后恢复和错误记录拒绝，没有运行实际模拟器。芯片、别名、整模型、cold4096、长解码、槽位复用、质量和性能门槛仍独立保留。
