# Nemotron Nano 9B：投影拆分问题与当前验证范围

2026-11-09 的 r8 运行仍在继续。以下记录的是已完成并保留实际退出与清理证据的 **14 项投影原语阶段**；它们不是整模型验收结果。当前没有新的 Nemotron 提速倍数。

当前测试使用 `vllm-neuron-ultra-nemotron9b-v1` 的提交 `60ab7f54a2c54ef0bc9b498621a45719ee7f0e84`，vLLM 0.11.0、Trainium1、原 BF16 输入和固定编译选项。正在运行的完整协议包含 52 个阶段，后续仍须完成卷积拆分、整模型编译、状态复制、数值、冷缓存、长解码、96 项质量检查、三轮工作负载及独立原始数据复核。新合并分支本身仍需单独验收。

每个阶段使用两种确定性输入，比较三个输出的全部字节，并检查输入没有变化。两种写法在 CPU 对照中均通过。原写法的失败是实验要复现的对照现象，因此“阶段完成”不等于“原写法数值通过”。设备结果来自已保留的工作进程记录，整套原始输出的独立复核尚未结束。

## 4096-token 用例中看到了什么

对输入 `[1,4096,11328]`，最后一个维度应拆成 `[5120,6144,64]`。我们重新读取并核对了两份小型 HLO 计算图的 SHA256，用纯 Python 解析 SDK 的 protobuf 描述，没有重新编译或运行模型。

原写法的图先把输入变成一维，再取连续区间，最后还原输出形状。例如第一份输出先取前 `4096×5120` 个元素，再变成 `[1,4096,5120]`。这样，第二个 token 的第一个元素取自输入偏移 **5120**，而逐 token 切片要求的偏移是 **11328**。

第二份输出也出现同类问题：图从展平输入偏移 `5120` 开始连续取 `4096×6144` 个元素，而正确行为应逐行取通道 `[5120,11264)`。第三份输出同样应逐行取 `[11264,11328)`。

替换写法使用原三维输入上的切片，保留 batch 和 token 两个维度，只在最后一维指定切分边界。4096-token 用例的 36,864 个结构地址抽样中，原图有 36,855 个不匹配，替换图为 0；两个确定性设备输入的三个完整输出也均为 0 字节差异。

因此，在这个固定复现用例中，问题已表现为计算图中的地址映射错误。该证据不能推广为所有 split、所有版本的 Neuron 或其他硬件上的行为，也尚未确定应归责哪个上游组件或提交。Dory 的 CPU 参考差异是另一项待定位问题，不能据此归因于 Trainium。

## 优化版本的使用边界

当前修复通过累计通道宽度构造显式边界，并调用 `torch.tensor_split`。先恢复正确计算，才能继续判断速度。失败的原实现不能作为提速倍数的分母；原语逐字节一致也不能替代整模型生成、长序列、请求槽位复用和实际四并发 HTTP 验证。
