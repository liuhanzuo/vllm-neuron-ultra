# Dory 系统库归属查询与 MiniCPM5 启动审查

Dory 的系统包信息采集已实际完成：32 次固定查询，父子进程均退出 0，主任务确认两个进程退出且子进程组为空。12 个目标均通过路径解析、包归属查询和该包文件列表交叉核对，找到唯一对应包。此次查询不读取库文件内容，因此官方包字节一致性与原生兼容性仍待验证，没有新增模型提速倍数。

退出后的独立审计也实际退出 0：重新取得原串行锁，完整核对输出文件与日志，并重算 32 条查询记录及最终完成事件。日志共 33 条、解压后 21,949 字节，输出占用 3,067,904 字节；保存的 1,318 组历史服务记录及描述符证据已核对。主任务随后独立确认审计进程退出。

## 查询发现

| 系统包（amd64） | 已安装版本 | 对应目标 |
|---|---|---|
| libc6 | 2.35-0ubuntu3.15 | 加载器、libc、libdl、libm、libpthread、librt、libutil |
| libgcc-s1 | 12.3.0-1ubuntu1~22.04.3 | libgcc_s |
| libgomp1 | 12.3.0-1ubuntu1~22.04.3 | 系统 libgomp 候选 |
| libnuma1 | 2.0.14-3ubuntu2 | libnuma |
| libstdc++6 | 12.3.0-1ubuntu1~22.04.3 | libstdc++ |
| libtcmalloc-minimal4 | 2.9.1-0ubuntu3 | libtcmalloc_minimal |

查询覆盖 25 个保存的路径名与别名。仍保留 11 条“按此名字查不到包归属”的原始记录，但每个目标的另一个已核对路径都能对应唯一软件包。原因是包数据库记录的路径与系统实际解析路径可以不同，例如包列表使用 `/lib/...`，文件最终解析到 `/usr/lib/...`；带版本号实体与未带版本号链接也不同。因此，单独一次 `dpkg-query -S` 查不到某个路径，不能推断库未安装或上游缺依赖。

这次补齐了之前未知的 libgomp、libnuma 版本，并明确接下来需要比对的六个官方包。未改变安装环境，未执行动态库加载器，也未选择两个 OpenMP 候选中的任意一个。原清单的 30 项来源、加载、缓存证据缺口仍保留，不能把包数据库元数据当作独立文件来源认证。

## 实验工具的改动

新增薄接入层复用原串行锁、历史检查、父子启动确认、进程组清理和资源限制。采集前，父子进程分别认证保存的外部依赖记录与缺口分类，要求路径范围恰好是原 12 个目标、25 个名字；命令限定为 25 次归属查询、一次六包版本查询及六次包列表查询。包列表中出现的新路径不会触发追加读取。

结果使用独立元数据格式，避免与完整环境清单混淆。原 2 GiB 地址空间、600 秒 CPU、900 秒墙钟、128 MiB 输出和存储下限保持不变。7 项接入测试经主任务复跑通过。

## MiniCPM5 的同期问题

真实外层启动、完整九项原生依赖认证及失败清理源码已交付，作者的 46 项模拟检查通过。接入时修正了服务查询漏取 `Nice` 属性，以及父子进程可能读取尚未写完的 JSON 记录两处问题；后者复用了已有的原子发布函数。

独立审查又发现一个尚待修复的启动阻断：子进程在本次服务已经运行后，嵌套调用原历史物理检查，其中未排除本次服务的并发检测会将其判为冲突。因此这组模拟结果不足以认定整条启动链可用，原生模型对照尚未执行。更深层的旧检查还错误假定当前子进程持有串行锁，而实际锁由外层进程保留。修复必须仅识别本次已绑定身份的服务，沿整条调用链使用外层锁观察，同时继续检查完整历史和其他并发任务。

独立复跑原 46 项模拟全部通过；新增 5 项内存控制实际走过上述嵌套判断并重现阻断，主任务也复跑通过。[独立审查](evidence/dory-system-packages-20261111/minicpm5-native-outer-independent-source-review-20261111-v1.md)明确拒绝将旧候选作为可启动版本，后继修复尚待独立核验。
