# MiniCPM5 新版运行器与独立退出后复核已接入源码

2026-11-10，MiniCPM5 的下一轮批大小／布局诊断补齐了新版 worker、runner、来源分类与独立退出后审核程序，相关源码和模拟检查通过并经过独立审查。Nemotron r12 已独立核实 27/52 个阶段，开始卷积拆分对照；完整模型流程仍在运行。本轮没有新增真实模型输出或提速倍数。

## 修复完整历史的接入问题

旧运行器第一版会拒绝历史来源映射中的原始载荷、系统查询依赖库及较大的元数据。新版保留全部来源与哈希，复用既有分类规则，明确区分文本、三个特殊编码 Python 文件、20 份历史原始载荷及九个查询依赖库。针对真实的 43,912 条 Nemotron 来源记录完成纯元数据分类检查，四个历史元数据别名保留；没有为通过检查删掉原始证据。

准备时只认证源码与元数据。外层取得原串行锁并完成前序实验排空后，才允许一次性认证固定九个依赖库，共 3,920,408 字节，并将完整认证记录的哈希绑定到运行准入。工作进程和独立审核器继承该记录并复核文件身份，不重复把系统库当普通源码或模型输入读取。原 8 MiB 普通文件上限与具名 32 MiB 元数据限制保留。

## 保留完整检查，减少重复历史扫描

新版没有抽样检查源码：每个来源仍完整认证。每次保护检查继续核对原串行锁、协调进程完整身份及性能窗口；上千个历史进程、已认证元数据身份和输出空间则在八个关键边界强制全量检查，并在持续工作中按一秒间隔复查。边界覆盖源码认证前后、历史数据认证、原生导入前、模型重放前后、worker 结束及 rank 输出前。

这解决了原实现每读取一份源码就重新扫描全部历史进程的开销。模拟测试中，44,000 次连续检查仍保留每次锁／进程／性能窗口检查，同时没有做 44,000 次完整历史扫描。它是启动和诊断执行的检查开销调整，不是模型推理提速数据。

原 TP2、16 GiB 内存限制、CPU 6–7、进程启动确认、失败清理、排空后才释放串行锁的规则保留。真实 Nemotron 完成记录仍是下一轮模型准入的前提。

## 独立退出后审核

新程序要求外部工具实际报告模型成功退出，再重获原串行锁，核对外层、协调进程及两个 rank 均已消失，原服务及全部历史服务已排空，认证记录没有被替换。随后重新读取全部 72 份完整输出，核对 144 次调用、24 个独立解码帧、原 own/restore/both 控制与每个张量视图公式。

独立审查发现，仅比较服务名集合会漏掉“某服务少了一次重复采样”的情况。现明确要求保存的和新观察的双采样均完整、相同，且包含服务属性与资源组证据。完整新排空证据以可无损还原的压缩 JSON 保存，并保留原审核器 2 GiB 内存、600 秒 CPU、900 秒墙钟及单文件 2 MiB 上限；真实资源表现仍需实际运行验证。
