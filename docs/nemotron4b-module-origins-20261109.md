# Nano4B：已加载模块核验与标准库来源清单

本轮补上已加载模块的来源核验，并接入此前的父进程放行、启动恢复和辅助程序测试流程。16 项模块核验和 17 项实际子进程集成检查通过，共 33 项。本轮仍属于运行准备，没有执行真实 SDK 或模型，也没有新增提速数字。

Python 导入模块时，可能直接返回 sys.modules 中已有的对象，不再经过查找器。因此，仅核验导入器不足以发现已加载模块被替换，或程序直接把一个未核验模块放进缓存。

新增检查会要求启动前的模块集合完整，并核验实际对象和固定的导入信息。之后新增的模块按源码、命名空间、解释器内置模块、原生扩展或明确授权的别名分别检查。源码模块必须使用所选的源码加载器，并与记录中的文件、包名和搜索路径一致；原生扩展仍需要实际原生库策略授权。

检查保留正常行为：可选导入失败后，其未初始化完成的模块可以消失；模块也可以重新导入或重新加载。两个集成测试专门确认，即使辅助程序输出了预期文本，替换已加载模块或直接注入模块后走缓存导入，仍会导致整次执行失败。

首次集成测试中，最终核验被直接调用，错误以 ValueError 返回，两个断言因此失败。未授权模块当时已经被拒绝；后续版本将最终核验接到统一的错误处理入口，保留原有拒绝条件，17 项检查全部通过。首次失败源码和实际退出结果均保留。

112 份硬链接源码位于 distutils 和 lib2to3。当前固定版本的读取器要求普通文件只有一个链接，会拒绝这些文件。下一步需要新增明确支持已记录硬链接身份的读取器，保留原始链接数量、完整文件身份和源码字节。系统文件没有被改动、重新链接或去重。

这份清单说明本机有哪些可核验的来源，不代表所有文件都会被实际导入，也不构成完整运行环境证明。当前模块检查关注导入身份和元数据，不能单独证明模块内所有代码与全局变量的来源。真实解释器、预加载代码与字节码、原生库映射、six.moves 和 distutils 别名规则仍需具体策略。

全部实际测试子进程已经回收。Dory 保存结果复核继续占用串行实验位置；它的原七项 FP32 检查失败仍未解释。后续模型范围、原精度、正确性与性能测试要求保持原定约束。
