## Nano4B 的启动连接发生了什么变化

新增 PhaseOriginContext 将此前独立准备的私有空缓存、解释器、原生文件映射、实际 typing 源码、冻结导入分发函数、模块来源、启动导入器和 six 别名检查连接起来。

构造时要求解释器和原生映射检查使用同一套记录，typing 与启动过程使用同一个缓存目录。先绑定标准解释器模块，再绑定别名和原始分发函数。其他预加载对象、源码提供者、别名目标和运行环境仍须由调用方明确认证；检查未通过时不能继续导入。

导入过程中保留原始导入器列表，允许经过认证的启动导入器按正常方式注册。six 的目标模块、共享别名与合法的模块描述变化通过已有专门策略处理。候选没有把这些兼容行为简化成全局放行。

restored_startup 现在直接把这个组合上下文接给 phase_site_restore v2，并提供 source／frozen site 的认证入口。这是后续工作进程可以调用的具体启动连接函数；真实主进程、rank、辅助进程的命令行和完整运行清单仍未接完。

## 组合测试覆盖了什么

两套原始 Python 环境各通过 26 项测试，共 52 次成功执行，包括：

- 实际 typing 源码、冻结分发函数和模块来源检查一起运行，执行生成的源码导入。
- 生成的启动导入器注册、six 移动目标、共享别名以及预加载目标的合法描述变化。
- 生成的 site 启动成功、启动函数异常、启动输出异常及源码认证拒绝。
- 源码修改、typing 代码对象替换、缓存目录出现文件、环境或预加载认证撤回时失败。
- 正常结束及异常结束后恢复两处导入分发入口；正常的可选 ImportError 仍可由调用代码捕获。

新启动测试最初失败，原因是测试检查器禁止所有 site 模块，把生成的测试 site 也拦住了。这个错误还让一个拒绝场景因错误原因通过。现已只允许明确生成的、通过源码加载器检查的 site 路径，并让拒绝测试匹配预期错误。初始失败输出和两份源码快照已保留。

本次使用生成的原生文件与映射记录，其他预加载来源和原生缓存包装器认证仍是测试替身；生成的 site、six、启动导入器不等于真实 SDK 启动。实际安装的 site 钩子、SDK、模型和原生库内容没有执行或显式读取。新增完整组合中的启动测试覆盖 source site 分支；Python 3.12 的真实 frozen site 组合尚未执行。

## Nemotron 9B：卷积消费者中的切分修复

卷积消费者输入为 BF16 [1,6144,T]，先转置，再按 [5120,512,512] 切分并恢复各消费者形状。候选保持原尺寸、精度和消费者，明确使用切分边界 [5120,5632]。

| 长度 T | 原方式：设备输出逐位一致 | 候选：设备输出逐位一致 | 原方式：抽查地址错位／总数 | 候选：错位 |
|---:|---:|---:|---:|---:|
| 128 | 0/6 | 6/6 | 1,143/1,152 | 0 |
| 256 | 0/6 | 6/6 | 2,295/2,304 | 0 |

两组原方式均在 CPU 检查和编译时成功，设备输出失败；候选的 12 次比较全部逐位一致，输入均未改变。128 长度下，第一个输出坐标 [0,1,0,0] 应读取输入偏移 1，原转换结果却读取了 655360。问题目前限定在已复现的软件环境和转换路径，没有独立归因到某个上游仓库或其他版本。

四个阶段都保留了正常退出记录。原方式正常退出表示预期失败已被复现，其内层数值结果仍为失败，不能用于计算提速。后续长度、整模型冷缓存至 4096、长解码、槽位复用、生成质量和真实 HTTP 配对性能仍在待验证范围内。
