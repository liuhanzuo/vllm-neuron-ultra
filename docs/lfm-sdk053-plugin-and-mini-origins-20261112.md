# LFM3 新版插件与 MiniCPM5 环境准备

2026-11-12：LFM3 的 vLLM-Neuron 0.5.3 迁移源码已发布到独立分支，提交 [`be4c914`](https://github.com/liuhanzuo/vllm-neuron-ultra/commit/be4c914bf33714101436341c81d752470e42e0c2)。[分支说明](https://github.com/liuhanzuo/vllm-neuron-ultra/blob/trn1-sdk053-lfm3-20261112/docs/lfm3-sdk053/README.md)包含实现范围与全部待完成的验证。**该分支尚未通过设备和整模型验证，没有新增提速倍数。** 原有已验证提速表保持原口径。

## LFM3 具体完成了什么

目标软件栈为 Python 3.12、vLLM 0.16、vLLM-Neuron 0.5.3、NxDI 0.10 和 NKI 0.5。固定原始 `LiquidAI/LFM3-1.7B` 权重版本，保留 BF16、TP2、数学核心与 tokenizer；候选范围是 B4/B8/B16、上下文 2048/4096。

| 改动 | 目的与验证边界 |
|---|---|
| 显式启用的模型注册 | 接入新版 vLLM、Transformers 与 NxDI；检测已有注册冲突。 |
| 独立编译产物身份 | 绑定模型、配置、源码和软件栈；在通用自动删除／重编译路径之前拒绝不完整或不匹配的产物。 |
| Typed NKI writer 接线 | 多行更新使用候选 writer，单行保留原操作；实际设备数值及 MUST_ALIAS 验证仍待运行。 |
| 新 runner 的 CPU sampler 接线 | 保留 execute、延迟采样、请求顺序恢复及 grammar mask 的顺序；保留显式随机生成器等回退行为。 |
| 请求生命周期检查 | 在修改槽位之前检查请求、位置和容量，拒绝未实现的抢占恢复、prefix cache、chunked prefill 等模式。 |
| 真实状态与调度预算分离 | 调度器使用含 null block 的 B+1 个代理块；设备模型仍有 B 个请求槽位、TP2 合计 70 个混合状态。代理预算不当作实际 HBM 占用。 |

主任务独立执行的 25 项标准库/mock 测试全部通过，另独立重放了 7 步完整 runner 生命周期模拟，覆盖 prefill、decode、暂未调度的请求、请求乱序、结束后同 ID 新请求、不同 prompt 长度和最终释放。模拟使用真实 runner 的状态更新与槽位方法，张量计算及采样输出仍为 mock。

29 份交付文件和 16 份原始来源均已核对。数学核心、helper、CPU sampler、tokenizer fixtures 及 typed wrapper/selector/dispatch 保持原字节；模型适配器的 AST 相同；typed JIT 只调整包内导入。原数值标准、冷缓存、1529 步长解码、槽位复用、quality96 和配对 HTTP 门槛完整保留。

完整 CPU r2 已成功结束：2026-11-12 06:33 UTC 观察到原工具会话退出 0，随后完整独立审计通过。原环境和新环境各生成 3,716 例测试数据，所有输入及预期输出的完整摘要一致；候选实现完成 123 批／1,648 例回归和 168 批／2,068 例扩展检查，全部通过。额外三路控制验证保留旧行为的失败、候选修正和恢复旧行为后的失败复现。

候选逐例检查输出形状、类型、全部位模式及输入不被改写，覆盖 BF16/FP32、不同容量、真实宽度与分块边界、无效槽位、重复槽位和请求重排。两套数据生成、候选执行及一个控制进程共 874 个实际子进程；主任务重读了所有启动确认、PID、启动时刻、命令、父进程及退出结果，确认全部退出 0，两个主进程和所有子进程均已消失，原串行锁可重新取得并已释放。

这轮修正仅作用于 NKI 0.5 **CPU 模拟器**的 BF16 输入回写：在固定输入提取位置保留 BF16 表示，避免不精确转换改写输入。原 SDK 文件未修改，包装在每批后恢复；设备 JIT 和模型服务不使用此包装。因此本结果证明完整 CPU 检查通过，尚不证明 TRN 上的写入别名、整模型质量或提速。后续设备矩阵仍为 105 个任务、127 图、4,304 项检查，包含 LFM 自身两个 KV 头的 4096 形状。

独立收尾审计还发现一个工具问题：原运行器会在成功退出后停止并卸载临时服务，第一次审计却要求当前服务继续保留历史退出码，因而失败。后继审计分别验证保存的原服务身份与真实退出 0，以及当前已卸载、无残留进程的状态，并重新执行全部科学检查。第一次失败与后继通过记录一并保留。核心原始记录、完整子进程清单、阶段汇总及审计源码见 [CPU 完整结果证据](evidence/lfm3-full-cpu-complete-20261112/manifest.json)。

## MiniCPM5 已明确的环境缺口

实际 SDK 使用 Python 3.10。已独立核对三份 APT 明文索引与既有签名 Release 记录、八个精确包地址；没有把 Python 3.12 的验证当作 Python 3.10 的验证。

此前缺少 Python 3.10 可执行文件、stdlib／动态 `_ctypes`、libffi 的完整归档及成员核验。现在八包下载与独立重放均已实际退出 0：三个必需包共 4,150,014 字节；另五个候选依赖共 2,960,850 字节，合计 7,110,864 字节。12 个选定成员与当前文件全部匹配。下载的 41 条事件与重放的 33 条事件分别由外部记录器复核，记录器自身退出也单独确认。候选依赖是否被实际加载仍未知，这一结果尚未建立完整原生依赖闭包，也没有新增模型提速。

现有 Dory 下载与 tar 核验实现可以复用，但旧输入绑定固定六包，旧 recorder 最多收 32 条事件；八包下载需要 41 条、重放需要 33 条，直接运行旧脚本会失败。最初六份后继源码保留旧 82 份来源摘要，共绑定 88 份源码。主任务独立运行 24 项标准库/mock 检查通过；当时的实际文本认证也独立通过，核对八包、12 个目标及 14 处索引条目。后续增加严格的历史服务核验，目前完整保留 98 份来源；最新流程的 16 项测试和计划构建器的 19 项测试均经主任务独立执行通过。

归档准备是独立串行步骤，使用原 inventory 的 128 MiB 总输出预算；原 Mini 科学诊断的 9 项原生检查、1,284 行、900 秒、AS 2 GiB 和单文件 2 MiB 限额保持不变。

MiniCPM5 前三轮包准备均在创建下载目录及启动子进程之前退出 1。第一轮发现两个旧服务已经卸载，当前状态不再保留原实例标识。后继验证原始退出、清理及独立记录器证据，再检查当前无残留；原失败和原成功退出分别保留，不把缺失记录补成成功。

第二轮通过完整历史检查后，发现两份系统 APT 明文索引已变化，因完整字节校验不符而停止。随后在独立串行步骤中，从原签名阶段保存的三个 XZ 重建了固定索引快照：先核对压缩文件完整摘要，再限定解压内存和长度，核对明文完整摘要、EOF 及精确尾流。三份只读快照合计 50,319,218 字节，最大单文件 22,511,228 字节，符合原 64 MiB 单文件、128 MiB 总输出预算。实际执行及独立记录器均退出 0，七条事件和三个完整文件再次核对通过。系统索引未被覆盖，原逻辑索引、签名和包条目保持不变。

第三轮通过快照认证后，发现 `/var/lib/dpkg/status` 的完整摘要也已变化。保留的系统备份与原摘要完全匹配；新旧完整文件的 1,521 个包记录中，仅两个 GStreamer 包的版本与安装大小发生变化，合计四处字段。八个目标包的完整记录和八份文件清单均未变化。后继显式绑定旧快照、新快照和当前状态，每次重新核对全文件摘要与精确差异，再用当前记录检查安装状态。主任务独立执行的 11 项测试通过，第四轮随后成功下载；原失败与新观察均保留。运行来源由原 98 项依次增至 100／103／106 项，每个旧摘要均保留，仅扩大源码条目数量上限，原源码字节限制、实验预算及模型门槛不变。

完整包归档核验包含版本、签名来源、tar 成员、完整文件内容和当前文件身份；重放逐包比较完整结果。包准备没有安装或替换 SDK 文件。新旧索引、状态观察、下载及重放的证据见 [本轮完整证据](evidence/minicpm5-sdk310-snapshot-and-archives-20261112/manifest.json)。

还发现旧的本地诊断记录器把 `original_sdk_model_exit_code` 固定写为 1，即使对应实际工具退出为 0。历史字段原样保留，判断退出依据真实工具、服务及子进程记录。该问题属于本项目诊断工具，不能归因于 vLLM-Neuron 上游，也不改变模型验收结果。两轮失败、修正源码和索引快照来源见 [Mini 包准备证据](evidence/minicpm5-sdk310-archive-attempts-20261112/manifest.json)。此前动态库映射失败的根因仍待后续原生验证。

## 接下来

LFM CPU r2 的完整结果与进程释放已核对，Mini 的固定索引、八包下载和独立重放也已完成。完整队列继续保留所有实际成功与失败，并另保留全部 874 个 LFM 子进程。Mini 的旧 libc6／新八包来源适配已通过独立源码审查，18 项检查通过，主任务也审阅了完整适配源码和两份前后差异。两套下载、重放和外部记录器证据分别核验，不合并成虚构的签名来源；原九项检查、1,284 行、900 秒及 AS 2 GiB 保持不变。

这些检查尚未建立实际原生依赖闭包。106 个来源阶段摘要只是完整运行源码的子集；源码审查还发现标准库路径会导入 `_struct`、Python 的 `zlib` 扩展和 `_blake2`，其实际提供者仍需观察，不能把 `libz.so` 当作 Python `zlib` 扩展本身。下一步先分别记录 Python 3.10 与外层 Python 3.12 在真实入口导入及 ctypes 导入前后的完整映射，再核对文件、ELF 依赖和六项 FFI 定义。遇到额外动态对象时补齐对应来源，之后才生成正式原生验证配置。

Qwen r6 的 API 启动失败仍待诊断；v8 会在原退出期限内保留完整异常和子进程状态。新增 v9 只补齐后续完整运行历史：从真实 LFM 退出记录及独立 scope/audit 取证，把全部 874 个子进程加入原检查范围，并核对三个已卸载服务的确定证据。四份运行代码除版本引用外与 v8 完全一致；主任务独立执行 10 项新增检查通过。

2026-11-12，r7 已通过外层完整运行解析、两次历史进程状态检查、源码及资源检查，实际协调进程已启动，并在期限内绑定真实工具会话 91085。仍使用原串行锁及完整配对流程。之前独立源码预检的失败来自主任务额外设置的导入拦截器：它拒绝了既有历史读取链中的 `ctypes`。该依赖与 r6 完全相同，原 outer 本来就在取得串行锁后解析；因此沿已审核的锁内路径执行，保留首次失败记录，没有修改历史代码或放宽模型标准。该导入也不能称为严格禁止 native 的纯元数据操作。整模型各阶段、quality96 和 HTTP 结果仍待实际完成；已修复的 Sampler 导入问题不能直接当作 r6 API 失败根因。本轮来源审查及实际启动记录见 [证据](evidence/qwen-r7-and-mini-composite-20261112/manifest.json)。

LFM 设备阶段仍需满足 30 GiB 保留空间加 24 GiB 输出预算。目前 NVMe 约有 43.1 GiB 可用，已退休数据的条件候选约 4.84 GiB，即使全部能回收也不足。`neuron-work` 和编译缓存中发现后续恢复及数值比较依赖，未删除；活动 swap、模型和待比较数据也保留。按用户不扩盘的要求，先推进输出较小的 Mini/Qwen 工作，同时保持 LFM 原预算和全部检查。没有为了启动实验降低保留线。

本页对应的原始记录见 [证据目录](evidence/lfm-sdk053-plugin-and-mini-origins-20261112/)。源码/mock 通过、环境准备和模型性能结果分别记录，只有完成原始全套验收的配对结果才会写入提速表。
