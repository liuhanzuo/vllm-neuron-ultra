# Nano4B：双分片启动与退出管理

Nano4B 的准备工作需要同时运行两个计算分片。此前已经有单进程握手与监督工具，但它不能直接解决“两个分片先一起就绪，再放行执行”的要求；逐个等待分片结束会阻止它们建立通信。

本轮补齐了双分片生命周期核心，18 项真实子进程检查通过。测试运行的是标准库模拟程序，没有加载实际 SDK、模型或权重。原生基线与提速仍未取得。

## 新增行为

程序先启动两个等待放行的分片，读取各自真实的进程身份、启动参数、父进程和所属进程组。两个分片都通过检查后，交给主程序持久化记录；再次检查身份和运行条件后才逐个放行。记录失败时，两个分片都不能开始实际工作。

两个分片放行后，程序同时读取四条输出管道，分别限制输出量和运行时间。任一分片失败时，会通过已经持有的内核进程句柄结束另一分片，并等待两者退出。记录保留原始退出码、发出的结束信号和可能不完整的输出；成功清理不会把失败实验改判为成功。

只放行第一个分片后，第二个放行步骤也可能失败。这种情况会保留已经发生的第一个放行记录以及完整身份记录，再回收实际启动的进程。身份记录使用独立副本，外部记录函数不能意外修改执行参数和原始证据。

## 验证范围

18 项检查覆盖以下行为：

- 两个分片在任一放行前都已记录，并能同时等待对方到达。
- 一方很快成功退出时，另一方仍可正常启动；双方大量输出也不会因管道阻塞而卡住。
- 一方异常退出时结束另一方；另一方忽略正常结束信号时，使用强制结束并记录实际退出。
- 就绪前退出、错误身份、记录失败、缺少记录凭证以及记录后的运行条件失败，均不能被报告为成功。
- 第二个进程启动失败、第二次放行失败、输出超限、超时和两个分片放行后的检查失败，均保留已经发生的操作并回收直接子进程。

所有测试中实际启动的直接子进程都已回收。另重新核验了原计划的 119 个源码指纹（5,552,337 字节）和已有握手工具的 5 个指纹，均未改变。

## 还缺什么

这是可以供主启动器调用的双分片管理核心。它尚未接入真实主启动器、SDK 辅助程序及原生模型工作进程。调用方仍须完成完整源码与环境核验、实际持久化记录、资源约束、辅助进程身份记录，以及整个所属进程组的退出检查。仅证明两个直接分片退出，不能证明所有辅助进程也已退出。

[SDK 依赖与启动检查](nemotron4b-helper-dependencies-20261109.md)中记录的剩余问题继续保留，包括启动环境恢复、动态导入与原生依赖。当前串行队列继续执行 Dory、已授权的有限存储维护、Nemotron 与 MiniCPM5 保存数据分析；Nano4B 真正启动时必须使用届时完整的任务历史。

原有精度、冷缓存至 4096、长解码、请求槽位复用、生成和质量、真实 HTTP C4、配对性能要求均未缩减。本轮没有新的模型正确性结论或提速倍数。
