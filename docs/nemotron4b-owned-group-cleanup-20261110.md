# Nano 4B：整组进程清理与结果衔接

本轮补上了原生基线启动器需要的进程组清理组件，并接入现有单进程、双进程管理器的结果格式，36 项检查通过。它解决的是“直接子进程退出后，如何确认实验没有留下其他进程”的准备工作。真实 SDK、模型服务和完整根启动器仍未运行，没有新增模型提速结果。

## 清理如何判定

直接子进程正常退出，不能证明 SDK 创建的后代进程也已退出。组件会同时检查服务是否终止、记录过的原进程是否消失，以及整个 cgroup 子树的进程列表和内核 populated 标志；需要两次一致的清空观察。

| 情况 | 处理 |
| --- | --- |
| 本次服务已自然退出，所有后代进程消失 | 保留实际服务退出值，再与直接子进程结果合并 |
| 仍有后代进程 | 核对本次服务身份后停止整组；必要时杀死该组所有进程 |
| 资源上限不符合要求 | 实验判失败，但仍允许清理已确认属于本次实验的服务 |
| 服务名称对应了另一次调用，或原命令、组路径变化 | 拒绝对这个新目标执行清理操作 |
| 同一 PID 已被复用 | 不把新进程当成旧实验进程，也不直接向该 PID 发信号 |
| 原进程仍存在，包括僵尸或移到组外的已记录进程 | 不能认定已清空 |

服务身份包含本次 nonce、完整启动命令、实际 invocation ID 和固定组路径。每次停止或杀进程组之前重新核对身份，并先保存操作意图。清理身份检查与资源检查分开，避免“资源配置错误，所以连本次失败实验也无法清理”的问题。

清理完毕与实验成功分别记录。只要需要强制清理、发生服务命令错误、子进程失败或服务非零退出，本次运行就不会变成成功结果。成功还要求此前真实捕获了服务主进程，终止记录中的主 PID 与该记录相符；其他后代进程不能代替主进程证据。组件本身始终不授权释放全局实验锁。

## 与现有代码衔接时发现的问题

现有单进程管理器使用 `successful`，双进程管理器使用 `direct_children_successful`；直接假定两者格式相同会导致接入错误。这是我们自身组件的接口差异，不是上游模型或 SDK 故障。

新适配器按原格式核对握手、双进程捕获、放行、实际退出和回收记录。原始 stdout/stderr 字节交给调用方完整保存，再引用该记录生成整组终止结果。如果结果格式不一致，或者原始输出保存失败，也会先尝试清理已经确认属于本次实验的服务，并保留失败。

## 验证范围与剩余工作

36 项检查覆盖嵌套进程组、残留后代、服务身份变化、正常退出与清理竞争、PID 复用、第二次观察时重新出现进程、输出保存失败和输出超限等情况。其中实际使用已有管理器启动并回收了轻量 Python 单进程和双进程；服务状态与 cgroup 数据使用生成的测试材料，没有启动、停止或杀死任何真实模型服务。

`systemctl` 不提供“仅当 invocation ID 仍相同时停止”的原子操作。因此实际根启动器还必须持有独占实验锁、使用新的固定服务名称，避免其他协作控制器在检查与操作之间替换服务。轮询与单次服务命令分别有限时，完整清理的总预算仍由实际根启动器约束。

剩余工作是完整根启动器、不可变的后继工作程序、主进程/两个计算进程/两个辅助进程的实际身份记录、原始输出保存，以及真实 SDK 的解释器和原生依赖接入。11 月 6 日的原 v2 合同与源码保持不变，不能直接当作已可运行版本。

Dory r3 保存结果复核仍在运行，原有七项 FP32 检查失败尚未解释。后续实验继续串行；本轮检查不会替代冷缓存、长解码、槽位复用、生成质量、HTTP C4 和配对性能测量。
